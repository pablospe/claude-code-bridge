# Milestone 5: Permission-prompt routing

> Status: Proposal, consumer-demand-gated. Deferred until a concrete consumer
> (e.g. T3 Code, an orchestrator dashboard) asks for permission-prompt
> routing.

## Goal

Surface claude's tool-permission prompts to the consumer UI, and route the
user's allow / deny decision back to claude. A remote-render UI — one where
the human approving Bash / Edit / Write is elsewhere — gets the prompt as a
`BridgeEvent`, shows it to the user, and replies through a bridge API. Claude
sees the decision the same way it would see a local terminal click.

## Mechanism (sketch)

The bridge's MCP server advertises the channels-native permission-routing
capability documented in the
[channels reference](https://code.claude.com/docs/en/channels-reference). The
bridge:

1. Surfaces incoming permission requests as a new (or reused) `BridgeEvent`
   variant. M1 already reserved `agent.input_requested` for this shape; M5
   should reuse it unless implementation reveals a concrete reason not to.
2. Adds a new bridge API for the response — shape roughly
   `bridge.respond(requestId, "allow" | "deny")` — that writes the decision
   back over the same channel transport.
3. Times out unanswered requests after a bounded window; the bound, the
   default, and the behavior on timeout (auto-deny vs surface-an-error) are
   open questions to be resolved when this milestone is picked up.

M5 does not introduce a new transport. It runs over the channel server's
existing JSON-lines control connection, with one new envelope variant per
direction (request out, response in).

## Why this is a separate milestone

- **Different protocol shape.** Hook relay is fire-and-forget. Permission
  routing is request / response with correlation ids and timeouts.
- **Different gating.** Per the public docs, the channels-native permission
  capability is governed by a separate server-side flag from the channels
  capability M1 already uses.
- **Different UX.** Latency-sensitive and interactive; a slow response is a
  bad user experience, not a missed log line.
- **Different testing matrix.** Round-trip tests, timeout tests, multi-prompt
  ordering tests.

Lumping permission routing with M3's observational hook relay inflates scope
without payoff for the 90% of consumers who just want a tool timeline.

## Why not now

No concrete consumer has asked. Investment in M5 is wasted until one does.
M3 ships the observational visibility that 90% of consumers actually need;
M5 picks up the moment a consumer wants the human-in-the-loop approval shape.

When a consumer does ask, the questions to resolve are:

- Reuse `agent.input_requested` or mint a new variant?
- Request-id source: bridge-generated or copied from the upstream prompt?
- Timeout default and behavior (auto-deny, surface error, fall back to
  default permission policy)?
- Does `bridge.respond` accept a string reason on deny?
- Multi-prompt ordering: queue, or surface as they arrive?

## Out of scope

Same set as M3:

- Token-level streaming and extended thinking blocks.
- Hook-driven behavior modification beyond permission routing.
- A separate websocket adapter for permission events.
- Multi-session permission routing in a daemon.
- Replay-from-cursor for `events(sessionId, {since})` based on permission
  records.
