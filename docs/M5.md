# Milestone 5: Publishing — plugin polish + npm release

> Status: Locked plan, ready to execute.

## Goal

After M5, a fresh user can install and run claude-code-bridge from public
artifacts — no `git clone`, no workspace knowledge. The two flows that work
end-to-end:

**Library / CLI consumer (programmatic):**

```bash
bun add claude-code-bridge          # or npm i, or pnpm add
bunx ccb demo --supervisor=claude "what is 11 squared?"
```

**Claude Code plugin user (tool-event visibility out of the box):**

```
/plugin marketplace add https://github.com/<owner>/claude-code-bridge
/plugin install ccb@claude-code-bridge
```

After plugin install, starting `claude` registers the ccb MCP server AND the
M3 hook relay automatically. A consumer reading the bridge event stream sees
`tool.event` records on day one, no `ccb hooks-config` step required.

The four gaps M5 closes (from the M3 review session):

1. `plugin.json` references `${CLAUDE_PROJECT_DIR}/packages/mcp-channel/src/bin.ts` —
   assumes the user starts claude from the bridge repo root. Remote-installed
   plugins do not have that property.
2. `plugin.json` declares the channel server but NOT the M3 hook relay. The
   shipped plugin gives no tool-event visibility unless the user manually
   runs `ccb hooks-config`.
3. Packages are `"private": true`. Nothing publishable to npm.
4. No documented Bun-vs-Node-runtime story for installed users.

## Non-goals

- **Drop the Bun runtime dependency.** The
  [`npx-runtime` worktree's `PLAN.md`](../.worktrees/npx-runtime/PLAN.md)
  tracks the Node-bundle path. M5 explicitly keeps Bun-on-PATH as the
  documented prereq; runtime portability is a separate, larger milestone.
- **Native binary compilation.** No `bun build --compile`, no `pkg`, no
  per-OS subpackages. The audience for that doesn't exist for an MCP bridge
  that already requires a JS runtime around it.
- **Windows support.** The bridge has never been tested on Windows. Path
  quoting, signal handling, PTY semantics all differ. Out of scope.
- **Claude Code marketplace listing.** Publishing the marketplace to Claude's
  official plugin directory (if such a directory exists / matures) is a
  follow-up coordinated with upstream. M5 ships the git-URL install flow
  only.
- **Versioned plugin compatibility matrix.** Phase 1 ships one version; the
  plugin manifest pins one major. Compatibility ranges land if and when a
  second major exists.

## Design (locked)

### Plugin manifest: path resolution

Plugin `command` invocations switch from
`bun ${CLAUDE_PROJECT_DIR}/packages/mcp-channel/src/bin.ts` to
`bunx ccb-channel-server`. The relay analogously becomes
`bunx ccb-hook-relay <event>`. This makes the plugin **stateless** with
respect to the bridge's source-tree layout — it's pure metadata pointing at
npm-installed bins.

`${CLAUDE_PROJECT_DIR}` is removed from `plugin.json` entirely. If a user
needs to point at a local checkout (development workflow), they continue to
use the `dev-flag` channels mode and the workspace bin paths, exactly as
today.

### Plugin manifest: hooks section

`plugins/ccb/.claude-plugin/plugin.json` gains a `hooks` section registering
`ccb-hook-relay` for all three minimum events (`PreToolUse`, `PostToolUse`,
`Stop`). Shape mirrors the snippet `generateHooksSettings` produces — the
two paths emit the same wire shape, so consumers see identical behavior
whether they install via plugin or via the managed-launch `hooks:` option.

```json
{
  "hooks": {
    "PreToolUse": [
      { "hooks": [{ "type": "command", "command": "bunx ccb-hook-relay PreToolUse" }] }
    ],
    "PostToolUse": [
      { "hooks": [{ "type": "command", "command": "bunx ccb-hook-relay PostToolUse" }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command", "command": "bunx ccb-hook-relay Stop" }] }
    ]
  }
}
```

### npm publishing: one package, no scope

Single package name: `claude-code-bridge`. Not scoped (`@org/name`), to keep
the install command short and the bin invocation discoverable via plain
`bunx`. The internal `@ccb/core` / `@ccb/mcp-channel` / `@ccb/claude-code` /
`@ccb/process` workspace packages stay private; only the top-level package
publishes.

Rationale for not publishing the workspace packages separately:

- The internal split exists for source-organization, not for consumer-facing
  composability. Consumers use `claude-code-bridge` as a black box.
- Multi-package publishing multiplies the version-coordination surface
  without payoff for any concrete consumer in scope.
- A flat top-level package keeps install instructions trivial and the
  semver story coherent.

The top-level `package.json` will re-export the public API surface from
`@ccb/core` via a built `dist/` (esbuild or `bun build`) and declare the
bins. Workspace packages remain `"private": true`.

### npm publishing: bin map

Top-level `package.json` gains:

```json
{
  "name": "claude-code-bridge",
  "version": "0.1.0",
  "private": false,
  "bin": {
    "ccb": "./dist/bin/ccb.js",
    "ccb-channel-server": "./dist/bin/ccb-channel-server.js",
    "ccb-hook-relay": "./dist/bin/ccb-hook-relay.js",
    "ccb-launcher": "./bin/ccb-launcher.cjs"
  },
  "files": [
    "dist/",
    "bin/ccb-launcher.cjs",
    ".claude-plugin/",
    "plugins/",
    "README.md",
    "LICENSE"
  ],
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": { "import": "./dist/index.js", "types": "./dist/index.d.ts" }
  }
}
```

`bun build --target=node` produces the `dist/` artifacts. The build is
deterministic and lives in `dist/` (gitignored). `prepublishOnly` runs
`bun run typecheck && bun test && bun run lint && bun run build` so a
broken publish is impossible.

### npm publishing: version policy

Phase 1 ships `0.1.0`. The semver discipline starts at 1.0.0 — until then,
every minor version is a potential break. M5's success criterion does NOT
include a 1.0 commitment; that's deferred until a concrete consumer adopts
the bridge and asks for stability guarantees.

### Bun-on-PATH documented prereq

`README.md` and the published package's npm description state Bun as a hard
dependency. `bunx ccb-channel-server` works on any host with Bun installed;
Node-only users get a clear "Bun required" error. The `npx-runtime` work,
when it lands, removes this constraint.

## Scope

1. **Plugin manifest refresh.** `plugins/ccb/.claude-plugin/plugin.json` —
   switch `command` strings to `bunx`-based invocations, add the `hooks`
   section, drop `${CLAUDE_PROJECT_DIR}`. Update `manifest.test.ts` to
   assert the new shape.
2. **Top-level `package.json` flip.** Remove `"private": true`, add
   `version`, `description`, `repository`, `license`, `bin` map, `files`,
   `main`, `types`, `exports`. Internal `@ccb/*` workspaces stay private.
3. **Build pipeline.** `bun run build` produces `dist/` with bundled bins
   (using `bun build --target=node`) and a single `index.js` re-exporting
   the public API surface. Add `dist/` to `.gitignore`. Add
   `prepublishOnly` script gating publish on the standard quality gates.
4. **Public API surface decision.** Decide which symbols from `@ccb/core` /
   `@ccb/claude-code` re-export through the top-level package. At minimum:
   `Bridge`, `BridgeEvent`, `JsonlEventStore`, `claudeCodeSupervisorFactory`,
   `mockSupervisorFactory`. Everything else stays internal.
5. **README install section.** First section in the README is the npm
   install + plugin install flow. Move the source-checkout flow to a
   "Development" section further down.
6. **Smoke test for the published shape.** A test that:
   - Runs `bun pm pack` (no actual publish).
   - Extracts the resulting tarball into `/tmp/`.
   - Verifies `dist/bin/ccb-channel-server.js` is executable, has the right
     shebang, and starts up to its arg-parse stage without crashing.
   - Verifies `plugins/ccb/.claude-plugin/plugin.json` is present in the
     tarball.
7. **Docs.** `docs/SMOKE.md` gains a "Real install from npm" section.
   `README.md` Install section is rewritten. `docs/ARCHITECTURE.md` gains a
   one-paragraph note on the published shape.
8. **CI gate** (optional, time-permitting). A GitHub Action runs
   `prepublishOnly` on every push to `main`. Out of scope if it would
   require setting up GH Actions infrastructure from scratch; in scope if
   the repo already has a workflow file.

## Task graph

Each task follows the M1/M2/M3 discipline: TDD red-green within the task,
commit on green, then `/pr-review-multi --models claude,gemini,codex`
against the local diff before moving on.

### M5.1 — Plugin manifest refresh (depends on nothing)

Files: `plugins/ccb/.claude-plugin/plugin.json`, `plugins/ccb/manifest.test.ts`.

Switch `command` to `bunx ccb-channel-server`. Add the `hooks` section per
the design above. Drop `${CLAUDE_PROJECT_DIR}` — the env var stays
referenced ONLY for `CCB_BRIDGE_ENDPOINT` / `CCB_SESSION_ID` placeholders.
Manifest tests assert the new shape.

### M5.2 — Build pipeline (depends on M5.1, parallel safe with M5.3)

Files: `package.json` (`scripts.build`, `prepublishOnly`), `.gitignore`,
a small `scripts/build.ts` (or `bun build` direct invocation in
`package.json`), test fixture for the build output.

Produce `dist/` via `bun build --target=node`. Bins get the right
`#!/usr/bin/env node` (or `bun`) shebang. Build is idempotent. CI gate not
required at this task; just a working local build.

### M5.3 — Top-level package.json un-private (depends on nothing)

Files: `package.json` only.

Remove `"private": true`. Add `version: "0.1.0"`, `description`,
`repository`, `license` ("MIT" or whatever Pablo chooses — open question
below), `bin`, `files`, `main`, `types`, `exports`. Keep workspace packages
private. Add a `LICENSE` file if missing.

### M5.4 — Tarball smoke test (depends on M5.2 and M5.3)

Files: `scripts/smoke-tarball.ts`, `package.json` (script entry).

`bun pm pack` produces a tarball; extract, sanity-check the bin shebangs,
sanity-check the plugin manifest is present, and assert each bin handles
`--help` without crashing. Gate behind a `CCB_RUN_TARBALL_SMOKE=1` env var
mirroring the existing M3 integration test pattern, so it does not run on
every `bun test` (cleanup of `/tmp/` tarball extracts is slow enough to
matter at unit-test cadence).

### M5.5 — Install docs (depends on M5.1, M5.3)

Files: `README.md` (Install section rewrite), `docs/SMOKE.md` (Real install
from npm section), `docs/ARCHITECTURE.md` (one paragraph on published
shape).

Document the two install flows (library and plugin), the Bun prereq, the
two-step plugin-install dance (`/plugin marketplace add` then
`/plugin install`), and the link to `dev-flag` mode as the local-development
escape hatch.

### M5.6 — Dry-run publish (depends on M5.1–M5.5)

Not a code task; a manual checklist captured in this doc. Pablo runs
`bun publish --dry-run`, inspects the output, confirms the file list and
the metadata. No PR; the dry-run output is just verified, not committed.
The first real `bun publish` is the milestone exit.

**Parallelism plan.** M5.1, M5.2, M5.3 are independent. M5.4 joins M5.2 +
M5.3. M5.5 depends on M5.1 and M5.3. M5.6 is the final gate.

## Success criteria

- `bun run build` produces a `dist/` whose bins each `--help` successfully.
- `bun pm pack` produces a tarball; the gated smoke test extracts and
  validates it.
- `bun publish --dry-run` reports a clean publish with the expected file
  list, metadata, and one-package shape.
- `plugins/ccb/.claude-plugin/plugin.json` references only `bunx`-based
  commands; no `${CLAUDE_PROJECT_DIR}` paths remain.
- Plugin manifest includes the M3 hooks section, exercised by the existing
  M3.7 integration test (which already asserts ordering and coverage —
  M5.1 does not need to duplicate this).
- `README.md` opens with the npm install flow; the dev-checkout flow is
  documented but secondary.
- `bun test` stays green throughout.

## Open questions

These are unresolved AFTER the locked decisions above. None blocks
starting M5.1.

- **License choice.** Phase 1 picks one (MIT or Apache-2.0 are the
  conventional defaults). Held open because the answer is administrative,
  not technical.
- **Author / repository field values.** Public GitHub user or org name;
  whether to publish under a personal scope (`pablospe`) if the
  unscoped name `claude-code-bridge` is taken on npm. Resolve at M5.3
  implementation time.
- **`dist/` in-tree or out-of-tree.** Conventional npm practice is
  out-of-tree (`.gitignore` it, generate fresh on publish). The risk is
  that a misconfigured CI publishes stale build output. Adopt the
  conventional pattern and rely on `prepublishOnly` to enforce freshness.
- **`bunx` cache vs install location.** A fresh `bunx ccb-channel-server`
  downloads the package into Bun's cache; whether that satisfies claude's
  hook-spawn latency budget is unverified. If first-fire cold-start blows
  the 500 ms relay budget, M5.6 documents a `bun add -g
  claude-code-bridge` prerequisite for hook-mode users. Verify during
  M5.4's tarball smoke; revise docs if needed.
- **Auto-bumping the version on every push.** Out of scope for phase 1
  (manual `bun publish` is fine); revisit if release cadence picks up.

## Out of scope

- Permission-prompt routing. That is M4 (separate, consumer-gated).
- The HTTP / WebSocket adapter and the ACP-compatible facade.
- `ccb attach <claude-pid>`.
- Token-level streaming, extended thinking, daemon mode, SQLite store.
- Multi-version compatibility matrix.
- Native binary builds, per-OS subpackages, Windows.
