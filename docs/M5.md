# Milestone 5: Permission-prompt routing

> Status: Implementation draft, NOT started, consumer-demand-gated. This is a
> design proposal worked out to the point where someone could pick it up and
> build it — it is not committed scope. No production code or tests exist yet.
> Deferred until a concrete consumer (e.g. T3 Code, an orchestrator dashboard)
> asks for permission-prompt routing.

## Goal

Surface claude's tool-permission prompts to the consumer UI, and route the
user's allow / deny decision back to claude. A remote-render UI — one where
the human approving Bash / Edit / Write is elsewhere — gets the prompt as a
`BridgeEvent`, shows it to the user, and replies through a bridge API. Claude
sees the decision the same way it would see a local terminal click.

The platform mechanism this builds on is the channels-native permission relay
documented in the
[channels reference](https://code.claude.com/docs/en/channels-reference#relay-permission-prompts).
Claude Code keeps the local terminal dialog open in parallel, so a decision
can still arrive from the terminal; whichever answer arrives first wins and the
other side is dropped. M5 is the remote side of that race.

## What the platform documents

Per the
[channels reference](https://code.claude.com/docs/en/channels-reference#relay-permission-prompts),
permission relay is a separate, opt-in capability on top of the base channel
capability M1 already uses:

- **Capability flag.** `capabilities.experimental['claude/channel/permission']`
  (always `{}`) declares the channel can receive permission-relay requests.
  This is distinct from `capabilities.experimental['claude/channel']`. Only
  declare it on a channel that authenticates its sender path — anyone who can
  reply through the channel can approve tool use in the session. The bridge
  control connection is loopback-only and bridge-internal, which satisfies that
  requirement, but the gating decision is the bridge owner's to make.
- **Outbound request.** Claude Code emits the MCP notification
  `notifications/claude/channel/permission_request`. `params` has four string
  fields:
  - `request_id` — five lowercase letters from `a`–`z` excluding `l` (so it
    never reads as `1`/`I`). Claude Code generates it; the channel echoes it.
    Claude Code only honors a verdict carrying an ID it issued.
  - `tool_name` — e.g. `Bash`, `Write`, `Edit`.
  - `description` — human-readable summary of the specific call (the same text
    the local terminal dialog shows).
  - `input_preview` — the tool's arguments as a JSON string, truncated to ~200
    characters.
- **Inbound verdict.** The channel sends back the MCP notification
  `notifications/claude/channel/permission` with two fields: `request_id`
  (echoing the issued ID) and `behavior` set to `'allow'` or `'deny'`. Allow
  lets the call proceed; deny rejects it like answering No locally. Neither
  verdict affects future calls. A verdict whose `request_id` matches no open
  request is silently dropped by Claude Code.
- **Scope.** Relay covers tool-use approvals (Bash, Write, Edit). Project-trust
  and MCP-server-consent dialogs do not relay; they stay local-only.
- **Versioning / gating.** Permission relay requires Claude Code v2.1.81 or
  later (the base channel capability requires v2.1.80). It is part of the
  channels research preview, so it carries the same enterprise policy and
  development-flag gating as M1.

The bridge's MCP server is the channel here, and its TCP control connection
(M1's `ControlServer`/`ControlClient`) is the link between the in-claude MCP
process and the out-of-process `Bridge`. M5 adds two control frames so the
permission request and verdict cross that link, and one event + one Bridge
method so the consumer can see the request and answer it.

## Architecture

```
claude (tool call needs approval)
  │  notifications/claude/channel/permission_request   (MCP, in-claude)
  ▼
channel-server.ts  (setNotificationHandler)
  │  control frame: { type: "permission_request", ... }   (TCP JSON-lines)
  ▼
ControlServer  ──emit("permission-request")──▶  Supervisor
                                                   │ emit(BridgeEvent)
                                                   ▼
                                                 Bridge ──▶ bus + JSONL store
                                                   ▲                │
                                                   │                ▼
                          bridge.respond(requestId, "allow"|"deny") consumer UI
                                                   │
  control frame: { type: "permission_response" }  │  (TCP JSON-lines)
  ▼                                                │
ControlClient (channel-server.ts) ◀───────────────┘
  │  notifications/claude/channel/permission        (MCP, in-claude)
  ▼
claude (verdict applied; tool proceeds or is rejected)
```

The outbound `permission_request` notification arrives at the MCP server via
`server.setNotificationHandler(...)` (the same SDK surface the docs use), not as
a tool call. The inbound verdict is emitted with `server.notification(...)`,
exactly like `deliver()` already emits `notifications/claude/channel`.

## The event

Mint a new `BridgeEvent` variant rather than reusing the reserved
`agent.input_requested`.

```ts
| {
    type: "permission.requested";
    sessionId: string;
    requestId: string;
    toolName: string;
    /** Human-readable summary of the call (claude's `description`). */
    description: string;
    /** Tool args as a JSON string, truncated to ~200 chars by the platform. */
    inputPreview: string;
  }
```

The terminal verdict is also persisted, as its own variant, so the JSONL store
records the full request/response pair (see [Persistence](#persistence)):

```ts
| {
    type: "permission.resolved";
    sessionId: string;
    requestId: string;
    /** "allow" / "deny" from a consumer verdict, or "timeout" / "terminal". */
    outcome: "allow" | "deny" | "timeout" | "terminal";
  }
```

### Why a new variant, not `agent.input_requested`

M1 reserved `agent.input_requested` with the shape
`{ sessionId; requestId; prompt }`. That fits a free-text "claude is asking the
user a question" interaction, not a structured tool-approval prompt. The
permission request has a fixed four-field schema (`tool_name`, `description`,
`input_preview`) that does not map onto a single `prompt` string without lossy
flattening, and the response is a closed `allow`/`deny` enum rather than free
text. Overloading `agent.input_requested` would force consumers to sniff the
field set to tell the two interactions apart. The two should stay separate
events; `agent.input_requested` remains reserved for an eventual free-text
elicitation feature.

(If a future maintainer disagrees, the fallback is: reuse
`agent.input_requested`, carry the four fields inside `prompt` as JSON, and
document the encoding. This draft recommends against it.)

## The response API

Add one method to the `ClaudeCodeBridge` interface and to `Bridge`, alongside
`sendMessage` / `interrupt`:

```ts
respond(sessionId: string, requestId: string, behavior: "allow" | "deny"): Promise<void>;
```

Behavior, mirroring `sendMessage` / `interrupt` in `bridge.ts`:

- `#requireSession(sessionId)`; reject with the existing `"session is closing"`
  error if the session is not `open`.
- Reject if `requestId` is not a currently-open request for this session (see
  [Correlation & lifecycle](#correlation--lifecycle)). This is a local guard so
  the consumer gets a real error; Claude Code would otherwise just silently drop
  an unknown ID.
- Call `session.supervisor.respond(sessionId, requestId, behavior)`, which
  writes the `permission_response` control frame to the channel server. The
  channel server emits `notifications/claude/channel/permission`.
- Persist a `permission.resolved` event with `outcome: behavior` via the
  awaited emit path (`#emitAwaited`), so the verdict is durable before the call
  resolves.

`respond` does not return a value: Claude Code does not acknowledge the verdict
(notifications are fire-and-forget per the docs), and the tool's actual outcome
surfaces later as ordinary M3 `tool.event`s. A `Promise<void>` that resolves
once the verdict is written to the control socket is the honest contract.

**Deny reason:** the documented `permission` notification carries only
`request_id` + `behavior` — there is no reason field. So `respond` does not
accept a reason string. (Listed as resolved against the open question from the
prior proposal: no, because the wire has nowhere to put it.)

## Wire protocol

No new transport. Two new envelope variants on the existing JSON-lines control
connection in `packages/mcp-channel/src/control.ts`, added to the
`ControlMessageSchema` discriminated union.

Server → client (request, server-initiated, analogous to `deliver`):

```ts
const PermissionRequestMessageSchema = z.object({
  type: z.literal("permission_request"),
  requestId: z.string(),
  toolName: z.string(),
  description: z.string(),
  inputPreview: z.string(),
});
```

Client → server (verdict, client-initiated, analogous to `tool`):

```ts
const PermissionResponseMessageSchema = z.object({
  type: z.literal("permission_response"),
  requestId: z.string(),
  behavior: z.enum(["allow", "deny"]),
});
```

Both join `ControlMessageSchema`'s `discriminatedUnion("type", [...])`.

Direction note, against the existing transport: today the channel server (the
in-claude MCP process) is the `ControlClient` and the Bridge side is the
`ControlServer` (`deliver` flows server→client, `tool` flows client→server).
Permission relay matches that polarity cleanly:

- `permission_request` originates in claude → arrives at the channel server
  (`setNotificationHandler`) → the `ControlClient` sends it to the
  `ControlServer`. **This is a new client→server frame** — it travels the same
  direction as `tool`, so the `ControlClient` gains a `sendPermissionRequest`
  and the `ControlServer` gains a `permission-request` event.
- `permission_response` (the verdict) originates at the Bridge → the
  `ControlServer` writes it to the client → the channel server's `ControlClient`
  receives it and calls `server.notification(...)`. **This is a new server→client
  frame** — same direction as `deliver`.

So, concretely:

- `ControlClient` gains `sendPermissionRequest(requestId, toolName, description, inputPreview)`
  (writes via the existing `writeLineNormal`, like `sendTool`), and its
  `readLines` handler gains a `permission_response` branch that invokes a new
  `onPermissionResponse(requestId, behavior)` callback (added to
  `ControlClientOptions`, like `onDeliver`).
- `ControlServer` gains a `respond(sessionId, requestId, behavior)` method that
  looks up the per-session socket (reusing the `#sessionSockets` /
  `#waitForSessionSocket` machinery `deliver` already uses) and writes the
  `permission_response` frame; and a new `permission-request` event in
  `ControlServerEvents` that fires when a `permission_request` frame arrives.

`channel-server.ts` wiring:

- Add `claude/channel/permission: {}` under `capabilities.experimental`.
- Register a `setNotificationHandler` for
  `notifications/claude/channel/permission_request` (schema validates the four
  string params) that maps the snake_case params to camelCase and calls a new
  `onPermissionRequest` callback (added to `CreateChannelServerOptions`,
  alongside `onTool`/`onInitialized`). The wiring code calls
  `controlClient.sendPermissionRequest(...)`.
- Add a `respondPermission(requestId, behavior)` to `ChannelServerHandle`
  (alongside `deliver`) that emits
  `server.notification({ method: "notifications/claude/channel/permission", params: { request_id, behavior } })`.
  The `ControlClient`'s `onPermissionResponse` callback invokes it.

## Correlation & lifecycle

- **requestId source: copied from upstream, never bridge-generated.** Claude
  Code generates the five-letter ID and only honors a verdict carrying an ID it
  issued. The bridge must propagate `request_id` verbatim through the event and
  back through `respond`. (Resolves the prior proposal's open question.) The
  bridge does not parse, validate the alphabet, or rewrite it — "no magic"
  (CLAUDE.md): it is an opaque correlation token.
- **Open-request registry.** The Bridge tracks open requests per session
  (`Map<requestId, { toolName; timer }>` on the `Session` struct). A
  `permission.requested` event opens an entry; `respond`, a timeout, or a
  terminal-wins drop closes it. `respond` rejects on an unknown/closed ID.
- **Timeout bound + default + behavior.** Recommended default: a bounded window
  with **auto-deny on timeout** and a configurable bound via
  `BridgeOptions.permissionTimeoutMs` (default **120_000 ms**, validated as a
  positive integer like `startTimeoutMs`/`closeTimeoutMs`). On expiry the bridge
  emits `permission.resolved` with `outcome: "timeout"`, sends `behavior: "deny"`
  back over the wire, and closes the registry entry.

  Trade-offs considered:
  - *Auto-deny (recommended).* Fail-safe: an unanswered approval defaults to the
    least-privileged outcome, matching the security posture of a permission
    prompt. The local terminal dialog also stays open the whole time, so a real
    human can still approve there; auto-deny only fires if nobody answers
    anywhere.
  - *Surface-an-error (no verdict sent).* Leaves the call hung pending the
    terminal dialog; the consumer UI shows a stale prompt. Worse UX, and risks
    leaking an indefinitely-open registry entry.
  - *Fall back to the local permission policy.* Not the bridge's call to make —
    Claude Code already owns the local dialog and the policy. The bridge sending
    nothing is equivalent; sending an explicit deny is the safe, explicit choice.

  120 s balances "give a remote human time to see and answer a phone
  notification" against "don't leak registry entries forever." It is
  configurable for consumers with different latency profiles.
- **Terminal-wins drop.** If the terminal answers first, Claude Code applies
  that and the relayed request is never answered remotely. The bridge has no
  signal that this happened (the platform does not notify the channel), so the
  registry entry simply ages out and auto-denies — a no-op, because Claude Code
  drops a verdict for an already-closed request. Emit `permission.resolved` with
  `outcome: "timeout"` in that case; the consumer learns the prompt is stale
  when the subsequent M3 `tool.event` shows the tool already ran (or didn't).
  A dedicated `outcome: "terminal"` is reserved in the variant for a future
  platform signal but is not emittable today.
- **Multi-prompt ordering: surface as they arrive, no queue.** Each request is
  independently correlated by `request_id`, and Claude Code processes verdicts
  by ID, not by order. Queuing would add latency and a head-of-line-blocking
  risk for no benefit. The consumer may have several open `permission.requested`
  events at once and answer them in any order.

## Persistence

The request/response pair lands in the per-session JSONL store the same way
every other `BridgeEvent` does — through `Bridge`'s emit paths into
`JsonlEventStore`:

- `permission.requested` is persisted via the fire-and-forget supervisor path
  (`#emitFromSupervisor`) when the control event arrives, so it is tracked in
  `session.pending` and drained on close.
- `permission.resolved` is persisted via the awaited path (`#emitAwaited`)
  inside `respond`, so the verdict is durable before `respond` resolves. The
  timeout path emits `permission.resolved` through the same awaited write.

`readStoredEvents` / `events(sessionId)` then replay both, so a consumer can
reconstruct "claude asked to run Bash X; it was allowed/denied/timed-out" from
the log alone. No new store type; both variants are ordinary `BridgeEvent`s.

## Test matrix

Unit + smoke, following the project TDD pattern (red → green → commit):

- **Round-trip (allow).** Inject a `permission_request` control frame → assert a
  `permission.requested` event on the bus and in the store → call
  `bridge.respond(..., "allow")` → assert a `permission_response` frame with
  `behavior:"allow"` reaches the channel-server side and a `permission.resolved`
  `outcome:"allow"` is persisted.
- **Deny path.** Same, with `"deny"` end to end.
- **Timeout / auto-deny.** Open a request, never respond, advance past
  `permissionTimeoutMs` → assert a `permission_response` `behavior:"deny"` frame
  is sent and `permission.resolved` `outcome:"timeout"` is persisted, and the
  registry entry is gone.
- **Multi-prompt ordering.** Open requests A, B, C; respond C, A, B → assert
  each verdict carries the matching `request_id` and out-of-order answers are
  delivered correctly.
- **Unknown / closed requestId.** `respond` with an ID that was never opened, or
  that already resolved/timed-out → assert it rejects locally and writes nothing
  to the wire.
- **Disconnect mid-request.** Channel-role socket drops (`peer-close`) while a
  request is open → assert the session tears down (M2 supervisor-initiated
  close) and `respond` for that session rejects with the `"closing"` error; no
  orphaned timer leaks.
- **Channel-server contract.** `permission_request` notification with malformed
  params is rejected by the zod schema and does not crash the handler;
  capability `claude/channel/permission` is advertised in the server's
  `capabilities.experimental`.
- **Smoke.** A documented bidirectional smoke command (extending the existing
  smoke harness) that drives a real permission prompt and answers it through
  `bridge.respond`, mirroring the curl walkthrough in the channels reference.

## Why this is a separate milestone

- **Different protocol shape.** Hook relay is fire-and-forget. Permission
  routing is request / response with correlation ids and timeouts.
- **Different gating.** Per the public docs, the channels-native permission
  capability (`claude/channel/permission`, Claude Code v2.1.81+) is governed by
  a separate server-side flag from the channels capability M1 already uses.
- **Different UX.** Latency-sensitive and interactive; a slow response is a
  bad user experience, not a missed log line.
- **Different testing matrix.** Round-trip tests, timeout tests, multi-prompt
  ordering tests.

Lumping permission routing with M3's observational hook relay inflates scope
without payoff for the 90% of consumers who just want a tool timeline.

## Why not now

No concrete consumer has asked. Investment in M5 is wasted until one does.
M3 ships the observational visibility that 90% of consumers actually need;
M5 picks up the moment a consumer wants the human-in-the-loop approval shape.

## Open questions / risks

- **Server-side capability flag.** The bridge owner must decide whether to
  advertise `claude/channel/permission` at all. The docs warn to declare it only
  on an authenticated channel; the loopback control link is bridge-internal, but
  the consumer-facing API (whoever can call `bridge.respond`) is the real trust
  boundary. Out of scope for M5's wire work, but a deployment-time decision.
- **Research-preview gating (unverified at build time).** Permission relay needs
  Claude Code v2.1.81+ and the channels research preview, with the same
  enterprise-policy and `--dangerously-load-development-channels` gating as M1.
  The exact behavior when the running Claude Code is too old (the docs say it
  "ignores the capability") should be verified live — likely the
  `permission_request` notification simply never arrives, so M5 degrades to
  "no remote prompts," which is acceptable.
- **No verdict acknowledgement.** Notifications are fire-and-forget; the bridge
  cannot confirm Claude Code received or applied the verdict. The consumer learns
  the real outcome only from the subsequent M3 `tool.event`. If a consumer needs
  positive confirmation, that is a follow-on, not M5.
- **Terminal-wins is invisible to the bridge (unverified).** The docs describe
  the local dialog winning races but do not describe any signal to the channel
  when that happens. M5 assumes none and ages the request out via timeout. If a
  future platform version adds such a signal, wire it to the reserved
  `permission.resolved` `outcome: "terminal"`.
- **`input_preview` truncation.** Capped at ~200 chars by the platform. The
  bridge passes it through verbatim; consumers needing the full args must read
  the corresponding M3 `tool.event` payload, which carries the (separately
  truncated) full hook input.

## Out of scope

Same set as M3:

- Token-level streaming and extended thinking blocks.
- Hook-driven behavior modification beyond permission routing.
- A separate websocket adapter for permission events.
- Multi-session permission routing in a daemon.
- Replay-from-cursor for `events(sessionId, {since})` based on permission
  records.

Additionally out of scope for M5:

- Project-trust and MCP-server-consent dialogs (the platform does not relay
  these).
- A deny-reason string (the documented verdict notification has no field for
  it).
- Positive verdict acknowledgement from Claude Code.
