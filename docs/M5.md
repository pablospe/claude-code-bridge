# Milestone 5: Permission-prompt routing

> Status: Implemented 2026-06-12 via the tool-enabled `ccb api` facade
> ([plan](./2026-06-12-tool-enabled-api-plan.md)). Originally drafted as a
> consumer-demand-gated proposal; the consumer is `ccb api --allow-tools`
> (pre-approve an allowlist, auto-deny everything else that prompts). The
> design below remains the accurate description of how allow / deny decisions
> are relayed over channels. The permission relay was proven live against real
> `claude` by `scripts/spike-permission` (see
> [`docs/2026-06-12-spike-findings.md`](./2026-06-12-spike-findings.md)) and the
> full-stack facade round trip is `scripts/tools-smoke.py` (SMOKE.md, Smoke 7).

## Goal

Surface claude's tool-permission prompts to the consumer UI, and route the
user's allow / deny decision back to claude. A remote-render UI — one where
the human approving Bash / Edit / Write is elsewhere — gets the prompt as a
`BridgeEvent`, shows it to the user, and replies through a bridge API. Claude
sees the decision the same way it would see a local terminal click.

The platform mechanism this builds on is the channels-native permission relay
documented in the
[channels reference](https://code.claude.com/docs/en/channels-reference#relay-permission-prompts).
Claude Code keeps the local terminal dialog open in parallel, so a decision
can still arrive from the terminal; whichever answer arrives first wins and the
other side is dropped. M5 is the remote side of that race.

## What the platform documents

Per the
[channels reference](https://code.claude.com/docs/en/channels-reference#relay-permission-prompts),
permission relay is a separate, opt-in capability on top of the base channel
capability M1 already uses:

- **Capability flag (opt-in).** `capabilities.experimental['claude/channel/permission']`
  (always `{}`) declares the channel can receive permission-relay requests.
  This is distinct from `capabilities.experimental['claude/channel']`. The
  [channels reference](https://code.claude.com/docs/en/channels-reference#relay-permission-prompts)
  is explicit: *"Only declare the capability if your channel authenticates the
  sender, because anyone who can reply through your channel can approve or deny
  tool use in your session."* So the capability is **not** declared
  unconditionally. M5 gates it behind an explicit opt-in flag —
  `enablePermissionRelay`, default **off** — threaded through the
  channel-server / supervisor / bridge options (see
  [Capability opt-in](#capability-opt-in)). The bridge control connection is
  loopback-only and bridge-internal, which satisfies the authenticated-sender
  requirement, but whoever can call `bridge.respond` is the real trust boundary,
  so the decision to flip the flag on stays with the bridge owner.
- **Outbound request.** Claude Code emits the MCP notification
  `notifications/claude/channel/permission_request`. `params` has four string
  fields:
  - `request_id` — five lowercase letters from `a`–`z` excluding `l` (so it
    never reads as `1`/`I`). Claude Code generates it; the channel echoes it.
    Claude Code only honors a verdict carrying an ID it issued.
  - `tool_name` — e.g. `Bash`, `Write`, `Edit`.
  - `description` — human-readable summary of the specific call (the same text
    the local terminal dialog shows). Per the docs, for a Bash call this is
    Claude's description of the command, *or the command itself if none was
    given* — so consumers must not assume it is always a tidy summary; it may be
    the raw command string.
  - `input_preview` — the tool's arguments as a JSON string, truncated to 200
    characters.
- **Inbound verdict.** The channel sends back the MCP notification
  `notifications/claude/channel/permission` with two fields: `request_id`
  (echoing the issued ID) and `behavior` set to `'allow'` or `'deny'`. Allow
  lets the call proceed; deny rejects it like answering No locally. Neither
  verdict affects future calls. A verdict whose `request_id` matches no open
  request is silently dropped by Claude Code.
- **Scope.** Relay covers tool-use approvals (Bash, Write, Edit). Project-trust
  and MCP-server-consent dialogs do not relay; they stay local-only.
- **Versioning / gating.** Permission relay requires Claude Code v2.1.81 or
  later (the base channel capability requires v2.1.80). It is part of the
  channels research preview, so it carries the same enterprise policy and
  development-flag gating as M1.

The bridge's MCP server is the channel here, and its TCP control connection
(M1's `ControlServer`/`ControlClient`) is the link between the in-claude MCP
process and the out-of-process `Bridge`. M5 adds two control frames so the
permission request and verdict cross that link, and one event + one Bridge
method so the consumer can see the request and answer it.

### Capability opt-in

The permission capability is **opt-in and off by default**, because the docs
require it only on a channel that authenticates its sender path. The opt-in is
an explicit flag, threaded consistently:

- `BridgeOptions.enablePermissionRelay?: boolean` (default `false`) on the
  out-of-process `Bridge`.
- A matching flag on the supervisor factory / supervisor that owns the
  `ControlServer`, and on `CreateChannelServerOptions` for the in-claude
  channel server.
- The channel server declares
  `capabilities.experimental['claude/channel/permission'] = {}` **only when the
  flag is set**, and registers the `permission_request` notification handler
  only then. With the flag off, the channel advertises `claude/channel` exactly
  as M1 does today and Claude Code never forwards permission prompts to it —
  the entire M5 path is inert.

There is no auto-detection or fallback ("no magic", CLAUDE.md): a bridge owner
who wants remote approvals turns the flag on, having decided the
`bridge.respond` surface is sufficiently authenticated for their deployment.

### Launch-mode dependency of the verdict path

This repo carries a documented limitation (see `docs/SMOKE.md`): on an
individual (Pro/Max) account, **inbound** channel notifications are rejected on
the plugin path (`--channels plugin:ccb@<marketplace>` reports *"not on the
approved channels allowlist"* and drops them); only the
`--dangerously-load-development-channels server:ccb` + `--mcp-config` path
delivers inbound. The permission **verdict** is an inbound, server→claude
notification (`notifications/claude/channel/permission`) of exactly that kind.

So M5's viability is launch-mode-dependent and **must be verified live before
the feature is claimed working**:

- On the **dev-flag** path, inbound is proven to round-trip (M1 inbound deliver
  works there), so the verdict notification should apply.
- On the **plugin** path, the verdict is likely blocked by the same allowlist
  gate that blocks inbound deliver. The *outbound* `permission_request`
  notification (claude→server) travels the same direction as hook relay and may
  still arrive — so prompts could surface while verdicts cannot apply. That is
  **worse than no relay**: the consumer sees an approval prompt it is
  structurally unable to answer. If live verification confirms this, M5 must
  refuse to advertise the permission capability on the plugin path (or document
  it as dev-flag-only) rather than offering a dead-end approve button.

## Architecture

```
claude (tool call needs approval)
  │  notifications/claude/channel/permission_request   (MCP, in-claude)
  ▼
channel-server.ts  (setNotificationHandler)
  │  control frame: { type: "permission_request", ... }   (TCP JSON-lines)
  ▼
ControlServer  ──emit("permission-request")──▶  Supervisor
                                                   │ emit(BridgeEvent)
                                                   ▼
                                                 Bridge ──▶ bus + JSONL store
                                                   ▲                │
                                                   │                ▼
                bridge.respond(sessionId, requestId, behavior)    consumer UI
                                                   │
  control frame: { type: "permission_response" }  │  (TCP JSON-lines)
  ▼                                                │
ControlClient (channel-server.ts) ◀───────────────┘
  │  notifications/claude/channel/permission        (MCP, in-claude)
  ▼
claude (verdict applied; tool proceeds or is rejected)
```

The outbound `permission_request` notification arrives at the MCP server via
`server.setNotificationHandler(...)` (the same SDK surface the docs use), not as
a tool call. The inbound verdict is emitted with `server.notification(...)`,
exactly like `deliver()` already emits `notifications/claude/channel`.

## The event

Mint a new `BridgeEvent` variant rather than reusing the reserved
`agent.input_requested`.

```ts
| {
    type: "permission.requested";
    sessionId: string;
    requestId: string;
    toolName: string;
    /** Human-readable summary of the call (claude's `description`). */
    description: string;
    /** Tool args as a JSON string, truncated to 200 chars by the platform. */
    inputPreview: string;
  }
```

Every open request closes with exactly one `permission.resolved` event, so the
JSONL store records the full request/response pair (see
[Persistence](#persistence)):

```ts
| {
    type: "permission.resolved";
    sessionId: string;
    requestId: string;
    /**
     * "allow" / "deny" — a consumer verdict the bridge sent over the wire.
     * "unanswered-remotely" — the bridge stopped waiting (timeout / session
     *   end). The real outcome is unknown to the bridge: the terminal may have
     *   answered, or the call may still be pending. Read the subsequent M3
     *   `tool.event` to learn what actually happened.
     * "aborted" — the session ended or crashed with the request still open;
     *   the registry entry was flushed so the log never leaves a
     *   `permission.requested` permanently unresolved.
     * "terminal" — RESERVED, not emitted today. There is no platform signal
     *   that the local terminal won the race (see
     *   [Correlation & lifecycle](#correlation--lifecycle)); this value is
     *   carried for a hypothetical future signal only.
     */
    outcome: "allow" | "deny" | "unanswered-remotely" | "aborted" | "terminal";
  }
```

A terminal-only answer is **not** persisted as a `permission.resolved` verdict
today — the bridge has no signal that it happened. The `"terminal"` value is
reserved against a future platform signal and is never written by M5 as
specified. (YAGNI tension noted: keeping a reserved enum member the code never
emits is a minor wart; it is kept only so a later platform signal can slot in
without a schema migration. A maintainer who prefers strict YAGNI should drop
it and add it back when the signal exists.)

### Why a new variant, not `agent.input_requested`

M1 reserved `agent.input_requested` with the shape
`{ sessionId; requestId; prompt }`. That fits a free-text "claude is asking the
user a question" interaction, not a structured tool-approval prompt. The
permission request has a fixed four-field schema (`tool_name`, `description`,
`input_preview`) that does not map onto a single `prompt` string without lossy
flattening, and the response is a closed `allow`/`deny` enum rather than free
text. Overloading `agent.input_requested` would force consumers to sniff the
field set to tell the two interactions apart. The two should stay separate
events; `agent.input_requested` remains reserved for an eventual free-text
elicitation feature.

(If a future maintainer disagrees, the fallback is: reuse
`agent.input_requested`, carry the four fields inside `prompt` as JSON, and
document the encoding. This draft recommends against it.)

## The response API

Add one method to the `ClaudeCodeBridge` interface and to `Bridge`, alongside
`sendMessage` / `interrupt`:

```ts
respond(
  sessionId: string,
  requestId: string,
  behavior: "allow" | "deny",
  options?: { approver?: ApproverMeta },
): Promise<void>;
```

Behavior, mirroring `sendMessage` / `interrupt` in `bridge.ts`:

- `#requireSession(sessionId)`; reject with the existing `"session is closing"`
  error if the session is not `open`.
- Reject if `requestId` is not a currently-open request for this session (see
  [Correlation & lifecycle](#correlation--lifecycle)). This is a local guard so
  the consumer gets a real error; Claude Code would otherwise just silently drop
  an unknown ID.
- **Synchronously** clear the auto-deny timer and remove the registry entry for
  `requestId` **before** any async work (before the store write, before the wire
  write). This is the exactly-once guard: a concurrent second `respond` for the
  same ID, or a timer that fires in the same tick, finds no entry and rejects /
  no-ops. Doing this async would open a window where two verdicts race onto the
  wire for one request.
- Persist a `permission.resolved` event with `outcome: behavior` (and any
  approver metadata) via the awaited emit path (`#emitAwaited`) — see
  [Persist-vs-send ordering](#persist-vs-send-ordering) for why the persist
  comes before the wire write.
- Call `session.supervisor.respond(sessionId, requestId, behavior)`, which
  writes the `permission_response` control frame to the channel server. The
  channel server emits `notifications/claude/channel/permission`.

`respond` does not return a value: Claude Code does not acknowledge the verdict
(notifications are fire-and-forget per the docs), and the tool's actual outcome
surfaces later as ordinary M3 `tool.event`s. A `Promise<void>` that resolves
once the verdict is durable and written to the control socket is the honest
contract.

### `respond` on the `Supervisor` interface

`respond` is a new method, but the `Supervisor` interface today is only
`start` / `sendMessage` / `interrupt` / `close`. Adding a *required*
`respond(sessionId, requestId, behavior)` forces every implementation to grow
it: `ClaudeCodeSupervisor`, `ServeSupervisor`, `MockSupervisor`, the inline test
stubs scattered across the bridge tests, and the supervisor contract test.

Recommendation: make `respond` **optional** on `Supervisor`
(`respond?(...): Promise<void>`). Only the channels-capable supervisor (the one
that owns a `ControlServer` with the permission capability enabled) implements
it; everything else leaves it undefined and never grows a no-op stub. `Bridge`
guards: if `enablePermissionRelay` is on, the configured supervisor MUST provide
`respond` (assert at construction or first use); if a consumer calls
`bridge.respond` and the supervisor has no `respond`, reject with a clear
"permission relay not enabled for this session" error. This keeps the blast
radius to the one supervisor that actually relays, instead of editing five
implementations to add stubs that throw.

### Approver identity / audit

For a single-user bridge, who approved is implicit. For a multi-user consumer
(a shared dashboard where several operators can answer), `respond` and the
persisted `permission.resolved` record currently capture only the verdict, not
*who* gave it — there is no non-repudiation trail. The optional
`options.approver` arg above carries approver metadata (e.g.
`{ userId: string; displayName?: string }`) that the bridge persists into the
`permission.resolved` JSONL record. It never crosses the wire to Claude Code
(the `permission` notification has no field for it); it exists purely for the
local audit log. Default-absent so single-user consumers ignore it entirely.

**Deny reason:** the documented `permission` notification carries only
`request_id` + `behavior` — there is no reason field. So `respond` does not
accept a reason string. (Listed as resolved against the open question from the
prior proposal: no, because the wire has nowhere to put it.)

## Wire protocol

No new transport. Two new envelope variants on the existing JSON-lines control
connection in `packages/mcp-channel/src/control.ts`, added to the
`ControlMessageSchema` discriminated union.

Client → server (the request; client-initiated; same direction as `tool`,
since the request originates in claude and the channel server is the
`ControlClient`):

```ts
const PermissionRequestMessageSchema = z.object({
  type: z.literal("permission_request"),
  requestId: z.string(),
  toolName: z.string(),
  description: z.string(),
  inputPreview: z.string(),
});
```

Server → client (the verdict; server-initiated; same direction as `deliver`,
since the verdict originates at the Bridge and the `ControlServer` writes it to
the channel-server client):

```ts
const PermissionResponseMessageSchema = z.object({
  type: z.literal("permission_response"),
  requestId: z.string(),
  behavior: z.enum(["allow", "deny"]),
});
```

Both join `ControlMessageSchema`'s `discriminatedUnion("type", [...])`.

Direction note, against the existing transport: today the channel server (the
in-claude MCP process) is the `ControlClient` and the Bridge side is the
`ControlServer` (`deliver` flows server→client, `tool` flows client→server).
Permission relay matches that polarity cleanly:

- `permission_request` originates in claude → arrives at the channel server
  (`setNotificationHandler`) → the `ControlClient` sends it to the
  `ControlServer`. **This is a new client→server frame** — it travels the same
  direction as `tool`, so the `ControlClient` gains a `sendPermissionRequest`
  and the `ControlServer` gains a `permission-request` event.
- `permission_response` (the verdict) originates at the Bridge → the
  `ControlServer` writes it to the client → the channel server's `ControlClient`
  receives it and calls `server.notification(...)`. **This is a new server→client
  frame** — same direction as `deliver`.

So, concretely:

- `ControlClient` gains `sendPermissionRequest(requestId, toolName, description, inputPreview)`
  (writes via the existing `writeLineNormal`, like `sendTool`), and its
  `readLines` handler gains a `permission_response` branch that invokes a new
  `onPermissionResponse(requestId, behavior)` callback (added to
  `ControlClientOptions`, like `onDeliver`).
- `ControlServer` gains a `respond(sessionId, requestId, behavior)` method that
  looks up the per-session socket (reusing the `#sessionSockets` /
  `#waitForSessionSocket` machinery `deliver` already uses) and writes the
  `permission_response` frame; and a new `permission-request` event in
  `ControlServerEvents` that fires when a `permission_request` frame arrives.

`channel-server.ts` wiring:

- Add `claude/channel/permission: {}` under `capabilities.experimental` **only
  when `enablePermissionRelay` is set** (see [Capability opt-in](#capability-opt-in)).
- Register a `setNotificationHandler` for
  `notifications/claude/channel/permission_request`. Per the
  [channels reference](https://code.claude.com/docs/en/channels-reference#permission-request-fields),
  `setNotificationHandler` routes by a `z.literal` on the top-level `method`
  field, so the schema is both validator and dispatch key — it must include the
  method literal, not just the params:

  ```ts
  const PermissionRequestNotificationSchema = z.object({
    method: z.literal("notifications/claude/channel/permission_request"),
    params: z.object({
      request_id: z.string(),
      tool_name: z.string(),
      description: z.string(),
      input_preview: z.string(),
    }),
  });
  ```

  The handler maps the snake_case params to camelCase and calls a new
  `onPermissionRequest` callback (added to `CreateChannelServerOptions`,
  alongside `onTool`/`onInitialized`). The wiring code calls
  `controlClient.sendPermissionRequest(...)`.
- Add a `respondPermission(requestId, behavior)` to `ChannelServerHandle`
  (alongside `deliver`) that emits
  `server.notification({ method: "notifications/claude/channel/permission", params: { request_id, behavior } })`.
  The `ControlClient`'s `onPermissionResponse` callback invokes it.

### `oninitialized` ordering for the verdict

The channel server already gates the first outbound `deliver` on
`oninitialized` (Claude Code drops channel notifications sent mid-handshake,
before the MCP `initialized` notification). The permission verdict is the same
kind of outbound `server.notification(...)`, so it is subject to the same
drop-if-too-early hazard. In practice a verdict can only be sent in response to
a `permission_request` that Claude Code itself emitted, which by definition
happens after the handshake completed — so a verdict is structurally
impossible to send "very early." Still, M5 should route `respondPermission`
through the **same** `oninitialized` gate `deliver` uses (rather than writing
directly), so the invariant is enforced in one place and a future code path
that tries to send a verdict early cannot silently lose it.

## Correlation & lifecycle

- **requestId source: copied from upstream, never bridge-generated.** Claude
  Code generates the five-letter ID and only honors a verdict carrying an ID it
  issued. The bridge must propagate `request_id` verbatim through the event and
  back through `respond`. (Resolves the prior proposal's open question.) The
  bridge does not parse, validate the alphabet, or rewrite it — "no magic"
  (CLAUDE.md): it is an opaque correlation token.
- **Open-request registry + where it opens.** The Bridge tracks open requests
  per session (`Map<requestId, { toolName; timer }>` on the `Session` struct).
  The entry **and** its auto-deny timer are opened in `#emitFromSupervisor`,
  which is where supervisor-pushed events arrive. A `permission.requested`
  branch is added there. Ordering matters relative to the existing
  `session.ended` short-circuit: that branch flips the session to `closing`
  synchronously and short-circuits; the `permission.requested` branch must run
  on the normal (non-terminal) path, and must not open a timer if the session
  is already `closing`/`closed` (the existing guard at the top of
  `#emitFromSupervisor` already drops events in those states — the registry
  open must sit after that guard so a request arriving during teardown is
  dropped rather than leaking a timer). Like the other timers in the codebase
  (`#waitForSessionSocket`, `raceWithTimeout`, the hello/ack timers), the
  auto-deny timer is `.unref()`'d so it never keeps the process alive.
- **`respond` closes synchronously.** As stated in
  [The response API](#the-response-api), `respond` clears the timer and removes
  the registry entry **before** any async work, so resolution is exactly-once.
- **Timeout bound + default + behavior.** Recommended default: a bounded window
  with **auto-deny on timeout** and a configurable bound via
  `BridgeOptions.permissionTimeoutMs` (default **120_000 ms**, validated as a
  positive integer like `startTimeoutMs`/`closeTimeoutMs`). On expiry the bridge
  removes the registry entry, sends `behavior: "deny"` back over the wire, and
  emits `permission.resolved` with `outcome: "unanswered-remotely"`.

  **Honesty of the timeout outcome.** Recording `outcome: "timeout"` would
  imply nobody answered anywhere — but that is not what the bridge knows. Claude
  Code keeps the local terminal dialog open the whole time; a human may have
  answered there, and the bridge gets no signal either way. So the outcome is
  `"unanswered-remotely"`: *the bridge stopped waiting; the real outcome is
  unknown — read the subsequent `tool.event`.* The deny the bridge sends is a
  bounded-memory hygiene action, not a claim about what happened.

  **Auto-deny is a real verdict, and it closes the terminal dialog.** Per the
  [channels reference](https://code.claude.com/docs/en/channels-reference#relay-permission-prompts),
  *"Claude Code applies whichever answer arrives first and closes the other."*
  An auto-deny sent over the wire **is** an arriving answer: if it lands while
  the terminal dialog is still open and unanswered, Claude Code applies the deny
  and **closes the terminal dialog**, foreclosing a terminal approval. A remote
  deny does not coexist with the terminal dialog; it cancels it. So the
  trade-off separates two distinct actions the bridge could take on timeout:

  - **(A) Drop the registry entry / stop tracking — send NO verdict.** Bounds
    bridge memory (no leaked entry or timer) while *preserving* the terminal
    answer path: the bridge simply stops waiting remotely and leaves Claude
    Code's local dialog untouched. A human at the terminal can still approve or
    deny. Fail-open-to-human. The cost: the consumer's remote prompt goes stale
    with no programmatic resolution, and if no human is at the terminal the call
    blocks until the terminal dialog itself is resolved or the session ends.
  - **(B) Send a deny verdict.** Force-denies and, by the docs, closes the
    still-open terminal dialog — actively foreclosing the terminal approval. Fail
    -safe-to-deny, but it overrides a human who may have been about to approve
    locally, on nothing more than a remote-side timer.

  **Recommendation: (A) — drop tracking, send no verdict.** The whole point of
  M5 is the away-from-terminal case, but a remote *timeout* is not evidence the
  human is absent; it is only evidence the *remote* side did not answer in
  `permissionTimeoutMs`. Letting a remote timer slam the terminal dialog shut
  (B) destroys the local human's still-valid opportunity to decide, which is a
  worse failure than a stale remote prompt. (A) bounds bridge memory — the
  stated goal of the timeout — without overriding the terminal. The bridge emits
  `permission.resolved` `outcome:"unanswered-remotely"` so the consumer can grey
  out the stale prompt, and the real outcome surfaces via the subsequent M3
  `tool.event`. A bridge owner who specifically wants fail-closed remote
  semantics can opt into (B) via a flag, but the default must not silently
  cancel the terminal.
- **Terminal-wins drop.** If the terminal answers first, Claude Code applies
  that and the relayed request is never answered remotely. The bridge has no
  signal that this happened (the platform does not notify the channel), so under
  recommendation (A) the registry entry simply ages out at
  `permissionTimeoutMs` and the bridge stops tracking — sending no verdict, so
  there is nothing for Claude Code to drop. The bridge emits
  `permission.resolved` `outcome:"unanswered-remotely"`; the consumer learns the
  prompt was stale when the subsequent M3 `tool.event` shows the tool already
  ran (or was rejected). The reserved `outcome:"terminal"` would be the value to
  use *if* a future platform signal told the channel the terminal won; no such
  signal exists today, so it is never emitted.
- **In-flight requests on session end / crash.** When a session transitions to
  `closing` (user close, supervisor-initiated close on channel disconnect, or
  crash) with registry entries still open, the close ladder must **flush each
  open entry** to the store as `permission.resolved` with `outcome:"aborted"`,
  and clear every pending auto-deny timer. This guarantees the log never leaves
  a `permission.requested` permanently unresolved — every request has a
  terminating `permission.resolved`. Because `#emitFromSupervisor` drops events
  once the session is `closing`/`closed`, this flush has to happen on the close
  path itself (alongside the `session.pending` drain in `#runClose`), not via
  the normal supervisor emit path. No verdict is sent on the wire during abort —
  the channel socket is being torn down anyway.
- **Multi-prompt ordering: surface as they arrive, no queue.** Each request is
  independently correlated by `request_id`, and Claude Code processes verdicts
  by ID, not by order. Queuing would add latency and a head-of-line-blocking
  risk for no benefit. The consumer may have several open `permission.requested`
  events at once and answer them in any order.

## Persistence

The request/response pair lands in the per-session JSONL store the same way
every other `BridgeEvent` does — through `Bridge`'s emit paths into
`JsonlEventStore`:

- `permission.requested` is persisted via the fire-and-forget supervisor path
  (`#emitFromSupervisor`) when the control event arrives, so it is tracked in
  `session.pending` and drained on close.
- `permission.resolved` is persisted via the awaited path (`#emitAwaited`)
  inside `respond`. The timeout / abort paths emit `permission.resolved` through
  the same awaited write.

### Persist-vs-send ordering

`respond` must **persist `permission.resolved` before writing the verdict to
the wire**, matching `bridge.ts`'s `sendMessage` (which `#emitAwaited`s
`message.sent` before calling `supervisor.sendMessage`) and honoring M5's own
"durable before resolve" goal. Persist-then-send is the required order:

1. Synchronously clear the timer + registry entry (exactly-once).
2. `await #emitAwaited(... permission.resolved ...)` — durable.
3. `await supervisor.respond(...)` — the wire write.

Failure semantics:

- **Store append fails (step 2):** `respond` rejects and **no verdict is sent**.
  The registry entry is already cleared, so the request will age out / abort,
  and the consumer gets a real error. No partial state where the verdict went
  out but the log has no record of it.
- **Wire write fails (step 3) after a successful persist:** the log records the
  verdict but Claude Code may not have received it. The bridge does **not**
  retry — notifications are fire-and-forget and a retry could double-apply if
  the first write actually landed. The consumer learns the true outcome from the
  subsequent M3 `tool.event`. (The inverse ordering — send then persist — is
  rejected: a store failure after a successful wire write would leave a verdict
  applied with no durable record, and any "retry the persist" is fine but a
  "retry the send" is not, so the asymmetry is cleaner with persist-first.)

Tests must cover store-append failure both **before** the wire write (verdict
suppressed, `respond` rejects) and the wire write failing **after** a durable
persist (record present, no retry, no crash).

`readStoredEvents` reconstructs "claude asked to run Bash X; it was
allowed/denied/aborted/unanswered-remotely" from the log alone via
`store.readAll()`. Note `events(sessionId)` is a **live tail from
subscribe-time forward** — it does not replay persisted records (the
`EventsOptions.since` field is reserved and currently ignored, per `bridge.ts`).
Replay-from-log is `readStoredEvents`; `events()` streams the request/resolve
pair live only while the session is active. No new store type; both variants are
ordinary `BridgeEvent`s.

## CLI / event formatting

The two new event variants need renderers in `apps/ccb/src/format.ts` if
consumers use the existing formatters. `formatJson` already covers any variant
(it `JSON.stringify`s the whole event), so the work is in `formatPretty`, which
is an exhaustive `switch (event.type)` with a `never` fallback — adding a
variant without a `case` is a type error. Add two arms, e.g.:

- `permission.requested` → `[permission.requested] <requestId> <toolName> <description>`
- `permission.resolved` → `[permission.resolved] <requestId> <outcome>`

mirroring the existing terse, single-line style (`[session.started] …`,
`[tool.event] …`). Until those arms exist, `formatPretty` will not compile once
the variants are added to `BridgeEvent`, so the renderer change is not optional
— it is forced by the exhaustiveness check.

## Test matrix

Unit + smoke, following the project TDD pattern (red → green → commit):

- **Round-trip (allow).** Inject a `permission_request` control frame → assert a
  `permission.requested` event on the bus and in the store → call
  `bridge.respond(..., "allow")` → assert a `permission_response` frame with
  `behavior:"allow"` reaches the channel-server side and a `permission.resolved`
  `outcome:"allow"` is persisted.
- **Deny path.** Same, with `"deny"` end to end.
- **Timeout (recommendation A).** Open a request, never respond, advance past
  `permissionTimeoutMs` → assert **no** `permission_response` frame is sent (the
  default does not slam the terminal), `permission.resolved`
  `outcome:"unanswered-remotely"` is persisted, and the registry entry + timer
  are gone. (If the opt-in fail-closed mode (B) is implemented, a separate test
  asserts a `behavior:"deny"` frame *is* sent under that flag.)
- **Multi-prompt ordering.** Open requests A, B, C; respond C, A, B → assert
  each verdict carries the matching `request_id` and out-of-order answers are
  delivered correctly.
- **Unknown / closed requestId.** `respond` with an ID that was never opened, or
  that already resolved/timed-out → assert it rejects locally and writes nothing
  to the wire.
- **Exactly-once under race.** Two concurrent `respond` calls for the same open
  ID (and a timer firing in the same tick as a `respond`) → assert exactly one
  verdict is written and exactly one `permission.resolved` is persisted; the
  second loses cleanly.
- **Persist-vs-send ordering.** (a) Store append rejects → `respond` rejects and
  no verdict frame reaches the wire. (b) Store append succeeds but the wire
  write rejects → the `permission.resolved` record is present, `respond` surfaces
  the wire error, no retry occurs, and nothing crashes.
- **Abort on session end.** Open requests, then close the session (and,
  separately, drive a supervisor-initiated close) → assert each open request is
  flushed to the store as `permission.resolved` `outcome:"aborted"`, all timers
  are cleared, and no `permission.requested` is left unresolved in the log.
- **Disconnect mid-request.** Channel-role socket drops (`peer-close`) while a
  request is open → assert the session tears down (M2 supervisor-initiated
  close), open requests are aborted (above), and `respond` for that session
  rejects with the `"closing"` error; no orphaned timer leaks.
- **Channel-server contract.** `permission_request` notification with malformed
  params is rejected by the zod schema (which keys on the top-level `method`
  literal plus `params`) and does not crash the handler; capability
  `claude/channel/permission` is advertised in `capabilities.experimental`
  **only when `enablePermissionRelay` is set**, and absent otherwise.
- **CLI / pretty formatting.** `formatPretty` in `apps/ccb/src/format.ts`
  renders `permission.requested` and `permission.resolved` (assert the new
  `switch` arms produce stable strings and the exhaustiveness `never` check
  still holds).
- **Smoke.** A documented bidirectional smoke command (extending the existing
  smoke harness) that drives a real permission prompt and answers it through
  `bridge.respond`, mirroring the curl walkthrough in the channels reference. Run
  on the **dev-flag** launch path (the only path proven to deliver inbound; see
  [Launch-mode dependency](#launch-mode-dependency-of-the-verdict-path)).

## Why this is a separate milestone

- **Different protocol shape.** Hook relay is fire-and-forget. Permission
  routing is request / response with correlation ids and timeouts.
- **Different gating.** Per the public docs, the channels-native permission
  capability (`claude/channel/permission`, Claude Code v2.1.81+) is governed by
  a separate server-side flag from the channels capability M1 already uses.
- **Different UX.** Latency-sensitive and interactive; a slow response is a
  bad user experience, not a missed log line.
- **Different testing matrix.** Round-trip tests, timeout tests, multi-prompt
  ordering tests.

Lumping permission routing with M3's observational hook relay inflates scope
without payoff for the 90% of consumers who just want a tool timeline.

## Why not now

No concrete consumer has asked. Investment in M5 is wasted until one does.
M3 ships the observational visibility that 90% of consumers actually need;
M5 picks up the moment a consumer wants the human-in-the-loop approval shape.

## Open questions / risks

- **Capability opt-in is the owner's deployment decision.** M5 gates the
  capability behind `enablePermissionRelay` (default off; see
  [Capability opt-in](#capability-opt-in)). The docs warn to declare it only on
  an authenticated channel; the loopback control link is bridge-internal, but the
  consumer-facing API (whoever can call `bridge.respond`) is the real trust
  boundary. The wire work is in M5; flipping the flag on is a deployment-time
  decision the bridge owner makes after deciding `bridge.respond` is
  sufficiently authenticated for their consumer.
- **Research-preview gating (unverified at build time).** Permission relay needs
  Claude Code v2.1.81+ and the channels research preview, with the same
  enterprise-policy and `--dangerously-load-development-channels` gating as M1.
  The exact behavior when the running Claude Code is too old (the docs say it
  "ignores the capability") should be verified live — likely the
  `permission_request` notification simply never arrives, so M5 degrades to
  "no remote prompts," which is acceptable.
- **No verdict acknowledgement.** Notifications are fire-and-forget; the bridge
  cannot confirm Claude Code received or applied the verdict. The consumer learns
  the real outcome only from the subsequent M3 `tool.event`. If a consumer needs
  positive confirmation, that is a follow-on, not M5.
- **Terminal-wins is invisible to the bridge (unverified).** The docs describe
  the local dialog winning races but do not describe any signal to the channel
  when that happens. M5 assumes none and (under recommendation A) ages the
  request out, stops tracking, and records `outcome:"unanswered-remotely"`. If a
  future platform version adds such a signal, wire it to the reserved
  `permission.resolved` `outcome:"terminal"`.
- **`input_preview` truncation.** Capped at 200 chars by the platform. The
  bridge passes it through verbatim; consumers needing the full args must read
  the corresponding M3 `tool.event` payload, which carries the (separately
  truncated) full hook input.
- **`--dangerously-skip-permissions` / `bypassPermissions` makes relay inert.**
  When permissions are bypassed, Claude Code emits no permission prompts at all,
  so the `permission_request` notification never fires and the whole M5 path is
  silent. This is a **no-op, not a bug**: there is nothing to relay because
  nothing is being gated. The capability can remain declared; it simply never
  triggers. Consumers running in bypass mode should not expect
  `permission.requested` events.
- **Non-interactive `-p` mode is out of scope.** `claude -p` runs a one-shot,
  non-interactive turn and disables terminal-input tools, so a permission prompt
  likely never fires there. The bridge drives a long-lived *interactive*
  (managed-PTY) session; M5 targets that session only. Non-interactive /
  one-shot launch modes are out of scope.
- **Multiple channels declaring the permission capability (open question).** The
  docs describe a single channel relaying prompts and do not address fan-out
  when more than one connected channel declares `claude/channel/permission`. M5
  assumes the bridge is the sole permission channel. Open questions for live
  verification: does Claude Code forward `permission_request` to *every* capable
  channel, or only one? If it fans out, does the first verdict from *any* channel
  win (and the others get the silent-drop treatment for an already-closed ID)?
  Until this is verified, M5 should be deployed as the only permission-capable
  channel in a session.

## Out of scope

Same set as M3:

- Token-level streaming and extended thinking blocks.
- Hook-driven behavior modification beyond permission routing.
- A separate websocket adapter for permission events.
- Multi-session permission routing in a daemon.
- Replay-from-cursor for `events(sessionId, {since})` based on permission
  records.

Additionally out of scope for M5:

- Project-trust and MCP-server-consent dialogs (the platform does not relay
  these).
- A deny-reason string (the documented verdict notification has no field for
  it).
- Positive verdict acknowledgement from Claude Code.
