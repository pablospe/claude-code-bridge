# Milestone 4: Publishing — plugin polish + npm release

> Status: Locked plan, ready to execute. Folds the multi-model design review
> (claude / gemini / codex, 2026-05-19) — see "Decisions locked from the
> design review" below.

## Goal

After M4, a fresh user can install and run the bridge from public artifacts
— no `git clone`, no workspace knowledge.

**Library / CLI consumer (programmatic):**

```bash
bun add @pablospe/claude-code-bridge          # or npm i, or pnpm add
bunx ccb demo --supervisor=claude "what is 11 squared?"
```

**Claude Code plugin user (tool-event visibility out of the box):**

```bash
bun add -g @pablospe/claude-code-bridge       # one-time global install — required prereq
```

```text
/plugin marketplace add https://github.com/<owner>/claude-code-bridge
/plugin install ccb@claude-code-bridge
```

After plugin install, starting `claude` registers the ccb MCP server AND
the M3 hook relay automatically. A consumer reading the bridge event stream
sees `tool.event` records on day one, no `ccb hooks-config` step required.

The four gaps M4 closes:

1. `plugin.json` references `${CLAUDE_PROJECT_DIR}/packages/mcp-channel/src/bin.ts` —
   assumes the user starts claude from the bridge repo root.
2. `plugin.json` declares the channel server but NOT the M3 hook relay.
3. Workspace packages and the top-level package are `"private": true`.
4. No documented Bun-vs-Node-runtime story for installed users.

## Decisions locked from the design review

The 2026-05-19 multi-model review (claude / gemini / codex) flagged several
load-bearing issues; each is resolved below and the rest of the plan now
assumes these.

- **npm package name: `@pablospe/claude-code-bridge`** (scoped under the
  author's personal npm scope). The unscoped `claude-code-bridge` is taken
  on npm by user `egoist` (0.0.0 stub, 2025-09-03); the
  hyphen-dropped `claudecode-bridge` is available but a compromise. The
  scoped name is guaranteed (the `@pablospe` scope is the author's),
  matches the GitHub repo name exactly, and signals ownership. Scoped
  packages default to restricted on npm, so `publishConfig.access` is set
  to `"public"`. The GitHub repo name stays `claude-code-bridge`; the
  npm-installable name is the scoped form. See "Renaming the npm package
  later" below for the (bounded) migration path if the unscoped name is
  ever wanted.
- **Drop `bunx` from `plugin.json`.** All three reviewers warned that
  `bunx`-per-hook risks blowing M3's 500 ms relay budget on cold-cache
  fires (possible network round-trip; possible "install? [y/N]" prompt
  hang). Plugin manifest commands invoke bins by name (`ccb-channel-server`,
  `ccb-hook-relay <event>`) and rely on the global install having put them
  on PATH. `bun add -g @pablospe/claude-code-bridge` is documented as a hard prereq
  for plugin users.
- **MIT license**, decided now. License is not administrative — npm
  publishing requires a clean `license` field.
- **Mark native modules external in the build.**
  `@homebridge/node-pty-prebuilt-multiarch` ships `.node` binaries that
  bundlers mangle; it is declared `external` in `bun build` and bubbled to
  the root `package.json`'s runtime `dependencies`.
- **Bin shebangs lock to `#!/usr/bin/env node`** because the build targets
  Node (`bun build --target=node`). `ccb-launcher.cjs` is already
  Node-shebanged. The Bun-on-PATH prereq applies to the runtime that
  spawns these bins (claude's hook subsystem, the user's shell), not to
  the bins themselves.
- **TypeScript declarations via `tsc --emitDeclarationOnly`**, emitted into
  `dist/types/`. `bun build` does not emit `.d.ts`.
- **ESM-only public API**, documented loudly. `exports` declares only
  `import` + `types`. `ccb-launcher.cjs` is the one CommonJS holdout and
  stays a `.cjs` bin (not part of the library surface).
- **Local-dev loop**: contributors continue to use `dev-flag` channels
  mode (no plugin involved). When a contributor specifically wants to
  exercise the plugin path during development, they run
  `bun link @pablospe/claude-code-bridge` in the bridge checkout and
  `bun link --global @pablospe/claude-code-bridge` in the consumer scope. The plugin
  manifest still references bin names, so PATH resolution finds the linked
  bins.

## Non-goals

- **Drop the Bun runtime dependency.** The
  [`npx-runtime` worktree's `PLAN.md`](../.worktrees/npx-runtime/PLAN.md)
  tracks the Node-bundle path. M4 explicitly keeps Bun-on-PATH as the
  documented prereq; runtime portability is a separate, larger milestone.
- **Native binary compilation.** No `bun build --compile`, no `pkg`, no
  per-OS subpackages.
- **Windows support.** The bridge has never been tested on Windows.
- **CJS / dual-build.** ESM-only by design; documented in the README.
- **Claude Code marketplace listing.** Publishing the marketplace to
  Claude's official plugin directory (if such a directory matures) is a
  follow-up coordinated with upstream. M4 ships the git-URL install flow
  only.
- **Versioned plugin compatibility matrix.** Phase 1 ships one version.
- **Workspace-package publishing.** Internal `@ccb/*` packages stay
  `"private": true`. One published black-box artifact, one semver story.

## Design (locked)

### Plugin manifest: path resolution

`plugin.json` `command` strings invoke bins **by name**, relying on the
user's PATH being populated by a prior `bun add -g @pablospe/claude-code-bridge`:

```jsonc
{
  "mcpServers": {
    "ccb": {
      "command": "ccb-channel-server",
      "env": {
        "CCB_BRIDGE_ENDPOINT": "${CCB_BRIDGE_ENDPOINT}",
        "CCB_SESSION_ID": "${CCB_SESSION_ID}"
      }
    }
  },
  "channels": [{ "server": "ccb" }],
  "hooks": {
    "PreToolUse":  [{ "hooks": [{ "type": "command", "command": "ccb-hook-relay PreToolUse"  }] }],
    "PostToolUse": [{ "hooks": [{ "type": "command", "command": "ccb-hook-relay PostToolUse" }] }],
    "Stop":        [{ "hooks": [{ "type": "command", "command": "ccb-hook-relay Stop"        }] }]
  }
}
```

`${CLAUDE_PROJECT_DIR}` is removed. The `${CCB_BRIDGE_ENDPOINT}` and
`${CCB_SESSION_ID}` placeholders remain because they're populated by the
bridge at session-start, not at install time.

### Plugin install prereq: documented, enforced by error message

A user who runs `/plugin install ccb@claude-code-bridge` without first
running `bun add -g @pablospe/claude-code-bridge` will see claude fail to spawn the
MCP server (`ccb-channel-server: not found`). The README's install section
states the prereq prominently and the plugin description string in
`plugin.json` repeats it. There is no auto-install hook (claude's plugin
runtime doesn't run package managers); the error message is the contract.

### npm publishing: single scoped package

Package name: **`@pablospe/claude-code-bridge`**. The internal `@ccb/core`
/ `@ccb/mcp-channel` / `@ccb/claude-code` / `@ccb/process` workspace
packages stay private; only the top-level package publishes, with
`publishConfig.access: "public"` so the scoped publish isn't restricted.

Rationale for the flat-publish approach is unchanged from the original
plan: consumers use the bridge as a black box, multi-package publishing
multiplies the version-coordination surface, and a single semver story is
worth more than internal-composability appearance.

### Renaming the npm package later

The scoped name keeps coupling low so a future move to an unscoped name
(`claude-code-bridge` via a transfer from `egoist`, or `claudecode-bridge`)
stays a bounded migration, not a rewrite. The npm package name appears in
exactly four places:

1. `package.json` `name` field.
2. The install commands in `README.md` and `docs/SMOKE.md`.
3. The `bun add -g …` prereq string in `plugins/ccb/.claude-plugin/plugin.json`'s
   `description` (and the matching assertion in `manifest.test.ts`).
4. This doc.

Everything else — the bins (`ccb`, `ccb-channel-server`, `ccb-hook-relay`,
`ccb-launcher`), the marketplace name (`claude-code-bridge`), the plugin
name (`ccb`), the `/plugin install ccb@claude-code-bridge` command — is
**independent of the npm package name**. The plugin install flow does not
change at all under a rename.

Migration steps when/if the unscoped name is wanted:

1. Publish the new name as a fresh `0.x` (or re-publish current version).
2. `npm deprecate @pablospe/claude-code-bridge "renamed to <new-name>"`.
3. Update the four locations above.
4. Existing installs on the scoped name keep working (deprecated ≠
   removed) but surface the deprecation notice on install.

### npm publishing: package.json shape

```jsonc
{
  "name": "@pablospe/claude-code-bridge",
  "version": "0.1.0",
  "private": false,
  "license": "MIT",
  "publishConfig": { "access": "public" },
  "description": "Bridge that drives interactive Claude Code sessions from external UIs via the channels MCP surface.",
  "repository": { "type": "git", "url": "git+https://github.com/<owner>/claude-code-bridge.git" },
  "type": "module",
  "bin": {
    "ccb": "./dist/bin/ccb.js",

    "ccb-hook-relay": "./dist/bin/ccb-hook-relay.js",
    "ccb-launcher": "./bin/ccb-launcher.cjs"
  },
  "main": "./dist/index.js",
  "types": "./dist/types/index.d.ts",
  "exports": {
    ".": { "import": "./dist/index.js", "types": "./dist/types/index.d.ts" }
  },
  "files": [
    "dist/",
    "bin/ccb-launcher.cjs",
    ".claude-plugin/",
    "plugins/*/.claude-plugin/",
    "README.md",
    "LICENSE"
  ],
  "dependencies": {
    "@homebridge/node-pty-prebuilt-multiarch": "<pinned version>",
    "@modelcontextprotocol/sdk": "<pinned version>",
    "commander": "<pinned version>",
    "zod": "<pinned version>"
  },
  "scripts": {
    "build": "bun run build:bundle && bun run build:dts",
    "build:bundle": "bun build --target=node --outdir=dist --external @homebridge/node-pty-prebuilt-multiarch ...",
    "build:dts": "tsc -p tsconfig.publish.json --emitDeclarationOnly --outDir dist/types",
    "prepublishOnly": "bun run typecheck && bun test && bun run lint && bun run build && bun run smoke:tarball"
  }
}
```

### Build pipeline

`bun build --target=node` produces ESM bundles for `dist/bin/ccb.js`,
`dist/bin/ccb-channel-server.js`, `dist/bin/ccb-hook-relay.js`, and
`dist/index.js`. Externals (excluded from the bundle, declared as runtime
deps):

- `@homebridge/node-pty-prebuilt-multiarch` — native bindings; bundling
  breaks `__dirname` resolution to the `.node` file.
- `@modelcontextprotocol/sdk` — large, well-maintained, no reason to inline.
- `commander` — large; standard external.
- `zod` — runtime schema, used by control protocol; not large but inlining
  it inflates each bin separately.

Shebangs are written as `#!/usr/bin/env node` (M4.2 verifies this).

`tsc -p tsconfig.publish.json --emitDeclarationOnly` produces the `.d.ts`
files under `dist/types/`. A separate `tsconfig.publish.json` exists so the
declaration emit excludes test files and uses `composite: false`. The
public surface re-exported through `dist/index.js`:

```ts
// Locked public surface for 0.1.0. Anything not listed stays internal.
export { Bridge, type BridgeOptions, StartTimeoutError } from "@ccb/core";
export type { BridgeEvent } from "@ccb/core";
export {
  CRASH_AGENT_DONE_REASON,
  CRASH_SESSION_ENDED_REASON,
} from "@ccb/core";
export { JsonlEventStore } from "@ccb/core";
export type {
  ClaudeCodeBridge,
  EventsOptions,
  SendOptions,
  SessionHandle,
  StartSessionOptions,
} from "@ccb/core";
export {
  claudeCodeSupervisorFactory,
  mockSupervisorFactory,
  type ChannelsMode,
  type ClaudeCodeSupervisorOptions,
  type HookEvent,
} from "@ccb/claude-code";
```

Everything else from `@ccb/core` / `@ccb/claude-code` / `@ccb/mcp-channel`
/ `@ccb/process` is implementation detail and stays unexported. Adding a
new symbol to this list is a minor-version bump; removing or renaming
anything is a major.

### Version policy

Ship `0.1.0`. The semver discipline starts at `1.0.0`; until then, every
minor is a potential break. No 1.0 commitment in M4.

### Bun-on-PATH documented prereq

The README and the package's npm description state:

> Bun ≥ 1.3 must be installed and on PATH. The bridge spawns child processes
> through Bun in some paths (and the M3 hook relay imports from
> `@ccb/core`, which is bundled but still loaded under the runtime that
> claude's hook system picks). Pure-Node hosts are tracked separately
> (see the project's `npx-runtime` branch).

## Scope

1. **Pre-flight verification.** Confirm the package name `@pablospe/claude-code-bridge`
   is still available on npm at execution time (it was on 2026-05-19; a
   stub-publish to reserve the name is part of M4.6). Verify the Claude
   Code plugin schema actually accepts the `hooks` block as documented;
   smoke a hand-crafted manifest against a live `claude` if possible.
2. **Plugin manifest refresh.** `plugins/ccb/.claude-plugin/plugin.json` —
   command strings switch to bare bin names, add the `hooks` section, drop
   `${CLAUDE_PROJECT_DIR}`. Update `plugin.json` `description` to state the
   `bun add -g` prereq. Update `manifest.test.ts` to assert the new shape.
3. **Top-level `package.json` flip.** Un-private, locked metadata per the
   "package.json shape" section above, add `LICENSE` file (MIT).
4. **Build pipeline.** `bun run build` produces `dist/` with bundled bins
   AND `dist/types/`. Externals locked per the build-pipeline section.
   Bins get the `#!/usr/bin/env node` shebang. `.gitignore` updated.
   `prepublishOnly` gates publish on the standard quality gates **plus**
   the tarball smoke.
5. **Tarball smoke test.** `scripts/smoke-tarball.ts`:
   - `bun pm pack` produces a tarball; extract into a fresh `tmpdir`.
   - Assert each bin file has the right shebang.
   - Assert each bin starts and responds to `--help` without crashing
     (covers basic import-graph wiring).
   - Assert `plugins/ccb/.claude-plugin/plugin.json` is present and
     parseable.
   - Spawn `ccb-channel-server` from the extracted tarball under a fake
     `CCB_BRIDGE_ENDPOINT` pointing at a test-owned `ControlServer`;
     assert it connects and sends `hello` within 2 s. This is the
     functional-equivalent of gemini's "PTY validation" concern but
     focused on the channel server's import path, which is the actual
     load-bearing initialization.
   - Default-on in `bun test`. Tarball production + extraction is fast
     enough on every run that gating by env var (the original plan) buys
     little.
6. **End-to-end plugin install smoke.** `scripts/smoke-plugin-install.ts`,
   gated by `CCB_RUN_PLUGIN_SMOKE=1` (heavyweight, needs real claude):
   - Builds the tarball.
   - Creates a temporary directory; installs the tarball there via
     `bun install <tarball>` so `ccb-channel-server` and `ccb-hook-relay`
     land in `<tmp>/node_modules/.bin/`.
   - Prepends that `.bin` to `PATH`.
   - Points `$HOME` (or `$CLAUDE_HOME` equivalent) at a temporary claude
     config dir; installs the marketplace from the local repo file URL.
   - Runs the M3.7 deterministic prompt through real claude.
   - Asserts at least one `tool.event` lands and Pre/Post pairing is
     ordered.
   This is what proves the plugin actually works end-to-end. The M4.5
   doc clearly directs the user to run this gated test once before
   publishing.
7. **README + SMOKE.md install docs.** First section of README is the
   two-step install: `bun add -g @pablospe/claude-code-bridge` + plugin commands.
   `docs/SMOKE.md` gains a "Real install from npm" section that lists
   the gated end-to-end smoke and the manual install verification.
   `docs/ARCHITECTURE.md` gains one paragraph on the published shape.
8. **Dry-run publish.** Manual checklist: `bun publish --dry-run`,
   inspect file list and metadata. Verify the package name is still
   available (else branch). First real `bun publish` is the milestone
   exit.

## Success criteria

- `bun run build` produces a clean `dist/` with the right shebangs,
  externals respected, and `.d.ts` files for the locked surface.
- The default-on tarball smoke (M4.4) extracts a fresh tarball and runs
  `ccb-channel-server` successfully against a test-owned `ControlServer`.
  Bin `--help` invocations succeed. Plugin manifest is present.
- The gated end-to-end smoke (M4.5) drives a deterministic prompt through
  real claude with the plugin installed from a local tarball and asserts
  at least one `tool.event` per minimum event with ordering — the same
  shape as M3.7, but exercising the public install path rather than the
  managed-launch `hooks:` option.
- `bun publish --dry-run` reports a clean publish with the expected file
  list and metadata.
- `plugins/ccb/.claude-plugin/plugin.json` invokes bare bin names; zero
  `${CLAUDE_PROJECT_DIR}` references remain.
- `README.md` opens with the two-step install. The dev-checkout flow is
  documented but secondary.
- `bun test` stays green throughout.

## Open questions

- **Owner / repo URL.** The `repository.url` value depends on the public
  GitHub user/org. Resolve at M4.3 by reading `git remote get-url origin`
  once the repo is set up for publication.
- **Squat-prevention stub.** Whether to publish a `0.0.1` README-only
  stub immediately after M4.3 lands, to lock the name. Cheap insurance;
  decide during M4.7.
- **`bunx` cold/warm latency vs hook budget (revisited).** Now moot for
  hook invocations (we use bare bin names), but still relevant for
  `bunx ccb` library-side use. Document one-shot vs installed expectations
  in M4.6.
- **CI gate.** Whether a GitHub Action runs `prepublishOnly` on every
  push. Out of scope for phase 1; revisit once a CI setup exists in the
  repo.
- **Plugin schema verification.** Whether the manifest's `hooks` block
  is accepted by claude's plugin runtime as designed. Verify during M4.1
  by hand-running `/plugin install` from a local marketplace; if claude
  rejects the `hooks` shape, fall back to claude's settings.json layer
  (with a one-time setup step documented in M4.6). Outcome of this
  verification is a hard gate for M4.5.
- **Future migration to tsup.** A 2026-05-19 spike confirmed `bunup`
  (the Bun-native tsup equivalent) wraps `bun build` and inherits the
  same hacks: shebang prepending, `import.meta.main` lowering. Only
  `tsup` (esbuild) would actually remove those — at the cost of
  leaving the Bun ecosystem for the build step. The hacks now live in
  `scripts/build-post-process.ts` with WHY comments so the cost stays
  legible; revisit if Bun fixes the underlying issues upstream OR if
  the friction grows beyond what one file can absorb.

## Out of scope

- Permission-prompt routing. That is M5 (separate, consumer-gated).
- The HTTP / WebSocket adapter and the ACP-compatible facade.
- `ccb attach <claude-pid>`.
- Token-level streaming, extended thinking, daemon mode, SQLite store.
- Multi-version compatibility matrix.
- Native binary builds, per-OS subpackages, Windows.
- CJS dual-build.
- Auto-publish on push.
