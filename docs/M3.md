# Milestone 3: Observational hook-relayed visibility

> Status: Locked plan, ready to execute.

## Goal

After M3, a consumer reading `events(sessionId)` sees a tool timeline — the Bash
commands, Edit / Write / Read calls, Grep / Glob searches — interleaved with the
message-level events M1 already delivers. The render goes from "what claude
finally said" to "what claude did, in order, with what inputs and results."

Concrete delta for a prompt like "fix the bug in foo.ts":

Before M3 (M1 + M2 surface):

```
[session.started]  sid=…
[agent.reply]      "I'll take a look at foo.ts."
[agent.reply]      "Found and fixed the off-by-one on line 42."
[agent.done]       final=true
[session.ended]    reason="agent done"
```

After M3 (hook relay on, three minimum events registered):

```
[session.started]  sid=…
[agent.reply]      "I'll take a look at foo.ts."
[tool.event]       PreToolUse  Read   {file_path:"…/foo.ts"}
[tool.event]       PostToolUse Read   (1.2 KB, truncated:false)
[tool.event]       PreToolUse  Edit   {file_path:"…/foo.ts", old_string:"…"}
[tool.event]       PostToolUse Edit   ok
[agent.reply]      "Found and fixed the off-by-one on line 42."
[tool.event]       Stop        (end of turn)
[agent.done]       final=true
[session.ended]    reason="agent done"
```

The `tool.event` BridgeEvent variant was reserved during M1 for exactly this
purpose and is currently dead code. M3 makes it live.

## Non-goals

- **Token-level streaming.** Indefinitely deferred. Every available path
  (Agent SDK; `--print --output-format stream-json`) re-violates a stated M1
  non-goal. Channels deliver complete messages, not tokens.
- **Extended thinking blocks.** Indefinitely deferred for the same reason — no
  path that respects M1's non-goals.
- **Permission-prompt routing.** Deferred to M4 (consumer-demand-gated).
- **Hook-driven behavior modification.** `PreToolUse` can block tools or
  rewrite tool inputs; M3 stays strictly observational. The relay never writes
  a `permissionDecision` back.
- **Phase-2 hook events.** See "Deferred to phase 2" below.

## Design (locked)

### `BridgeEvent` shape: catch-all `tool.event`

```ts
{ type: "tool.event"; sessionId: string;
  payload: { event: string; data: unknown } }
```

Honors the variant M1 already reserved. `payload.event` is the hook event name
verbatim (`"PreToolUse"`, `"PostToolUse"`, `"Stop"`). `payload.data` is the
hook payload, after the size policy below has been applied. Consumers narrow
on `payload.event` at their convenience.

Rationale: hooks are an evolving surface owned upstream. Keeping the public
`BridgeEvent` union stable insulates consumers from churn in claude's hook set
and from any future renames. Promoting specific variants is a non-breaking
follow-up that can happen if a concrete consumer reports the introspection
cost.

### Identity and session correlation

The relay bin tags every frame with the value of its `CCB_SESSION_ID` env var,
the same variable the channel server already reads. The bridge filters and
routes by that tag.

The bridge does NOT inspect any `session_id` field that may appear inside the
hook payload itself. The hook's internal `session_id` is embedded in
`payload.data` verbatim for consumer use, but plays no role in bridge routing.
This sidesteps the question of whether claude's internal session id equals
`CCB_SESSION_ID`: M3 makes that question irrelevant.

### Minimum hook set (phase 1)

Exactly three events: `PreToolUse`, `PostToolUse`, `Stop`. Smallest set
sufficient to render a tool timeline plus an end-of-turn marker. See
"Deferred to phase 2" for the rest.

### Payload size policy

Hard cap of 64 KB (65 536 bytes, measured on the JSON-serialized field value)
per field on `tool_input` and `tool_result`. When truncated, set
`truncated: true` on the same object that holds the truncated field. The 64 KB
constant is not configurable in phase 1; it is documented in the spec.

Metadata fields (`tool_name`, `tool_use_id`, timestamps, anything that isn't
`tool_input` or `tool_result`) pass through whole.

Example, `tool_input` truncated:

```json
{
  "event": "PreToolUse",
  "data": {
    "tool_name": "Bash",
    "tool_use_id": "toolu_01…",
    "tool_input": { "command": "<first 64 KB of the command>" },
    "truncated": true
  }
}
```

### Readiness gate (shared with M2 — supervisor side shipped)

The "bridge is reachable" contract has two surfaces.

1. **`ClaudeCodeSupervisor.start()`** resolves only after the channel server's
   first `hello` for this session arrives at the bridge. Bounded by
   `Bridge.startTimeoutMs` at the layer above. **Shipped during M2** as
   commit `178b995` (supervisor side) plus `2443b47`
   (`ControlServer.deliver` waits for hello up to `deliverWaitMs`, default
   30s). M3 inherits this — no work needed.

2. **Hook relay bin (each fire)** runs its own short hello handshake before
   sending the `hook` frame. If the bridge is unreachable for any reason, the
   bin logs to stderr and exits 0. The bin MUST NOT fail claude's hook: a
   failing hook can block claude's turn, and observational visibility is not
   worth that risk. M3 owns this part.

The bridge tolerates hook frames received before the channel server's first
hello completes via a bounded in-memory queue: cap 100 frames per session,
oldest dropped on overflow, flushed after the channel-server hello arrives.
Hook frames received AFTER the channel server's peer-close are dropped
silently — the session is shutting down and there is no live consumer to fan
out to.

## Scope

1. **Relay bin.** `packages/mcp-channel/src/hook-relay.ts` plus a new bin
   entry `ccb-hook-relay`, mirroring `ccb-channel-server`'s structure. Reads
   the hook payload JSON from stdin, runs the hello handshake, sends one
   `hook` frame, exits 0.
2. **Control protocol extension.** Add the `hook` envelope variant to
   `ControlMessageSchema` in `packages/mcp-channel/src/control.ts`. Add a new
   `hook` event on `ControlServer`'s emitter; supervisor adapters listen and
   fan it into the bridge as `tool.event` records.
3. **Bounded pre-hello queue.** Per-session, cap 100 frames, oldest-dropped,
   flushed on hello, drained / discarded on peer-close.
4. ~~`supervisor.start` hello gate.~~ **Already shipped in M2** (`178b995`).
   No M3 work; see "Readiness gate" above.
5. **`ccb hooks-config` CLI subcommand.** Emits the settings.json snippet
   that registers the relay for the three minimum events. Accepts `--out
   <path>` to write the snippet; default is stdout. Phase 1 does not auto-
   merge into existing settings.json files — that decision is left as an
   open question (see below).
6. **Managed-launch integration.** `ClaudeCodeSupervisor` accepts a
   `hooks?: { events: Array<"PreToolUse" | "PostToolUse" | "Stop"> }` option.
   When set, the supervisor writes a temp settings.json registering the
   relay for the requested events and passes its path via `--settings`. Off
   by default; turning it on is one option flag.
7. **`formatPretty` rendering.** `apps/ccb`'s pretty renderer handles
   `tool.event` records on one line, e.g.
   `[tool.event] PreToolUse Bash "git status"`. Truncation is rendered as
   `(truncated)` next to the affected field.
8. **Docs.** SMOKE.md gets a hook-relay section. README adds a one-paragraph
   pointer.

## Success criteria

- Unit tests cover the new envelope, the bridge fan-in, the 64 KB truncation,
  the bounded pre-hello queue, the relay bin's three failure modes, and the
  `supervisor.start` hello gate.
- `bun run lint` and `bun run typecheck` stay green.
- `formatPretty` renders `tool.event` records on one line each. No raw JSON
  dumps in default output.
- A `CCB_RUN_REAL_CLAUDE=1`-gated integration test against real `claude`
  confirms `tool.event` records for at least one of each of `PreToolUse`,
  `PostToolUse`, and `Stop` land in the JSONL during a single managed-launch
  turn.
- Negative criterion: no M3 PR introduces a `stream-json` reader, a PTY-output
  parser for semantic content, or any `permissionDecision`-writing path.

## Deferred to phase 2 of M3

In-scope for M3 conceptually, but explicitly deferred from phase 1. Each gets
a one-line rationale.

- `SessionStart` — partially redundant with the bridge's existing
  `session.started`.
- `SessionEnd` — partially redundant with the bridge's existing
  `session.ended`.
- `UserPromptSubmit` — partially redundant with the channel `prompt` the
  bridge already records on the inbound path.
- `PreCompact` / `PostCompact` — low value per event for a tool-timeline UI;
  carry no tool data.
- `PostToolUseFailure` — useful but partially carried by `PostToolUse`
  payloads when claude's hook surface exposes failure as part of the same
  event; defer until phase 2 confirms the on-the-wire shape.
- `Notification` — broad catch-all; surfaces auth dialogs and unrelated
  events; low signal-to-noise for tool timeline.
- `SubagentStart` / `SubagentStop` — subagents' own tool calls surface via
  their own `PreToolUse` / `PostToolUse` already; the start/stop markers add
  value but are not part of the minimum tool timeline.

## Out of scope

- Permission-prompt routing. Deferred to M4 (see `M4.md`).
- Hook-driven behavior modification (block tool calls; modify prompts;
  write `permissionDecision`).
- A separate websocket adapter for hook events. The HTTP / WS adapter is its
  own future milestone; M3 ships hooks over the existing transport only.
- Multi-session hook routing in a daemon. Per M1, the bridge is library +
  per-invocation CLI; no daemon.
- Replay-from-cursor for `events(sessionId, {since})`. The JSONL store
  records `tool.event` rows the same way it records every other event;
  cross-process replay remains deferred per M2's Out of Scope.

## Open questions

These are genuinely unresolved AFTER the locked decisions above. None of them
block starting M3.1.

- **Auto-merge vs documented-only `hooks-config`.** Phase 1 emits the snippet
  to stdout / `--out`. Should `ccb hooks-config --merge ~/.claude/settings.json`
  exist as an explicit opt-in for users with no pre-existing hooks? Auto-merge
  risks breaking unrelated hook entries; documented-only adds friction. Held
  open because the answer depends on how often consumers want this outside the
  managed-launch path, which already sidesteps the question entirely.
- **`tool.event` payload encoding for very small values.** The 64 KB cap
  decides truncation, but unclear: do we JSON-stringify-and-measure each field
  independently, or measure the serialized payload object as a whole and
  truncate the largest field? Two valid interpretations of "per-field 64 KB";
  needs a decision during M3.1 implementation but does not change the public
  contract.
- **Hook relay reconnect behavior on transient bridge unavailability.** The
  bin opens a fresh TCP connection per fire and exits 0 on failure. A flaky
  bridge (e.g. mid-restart) loses observability silently. No retry in phase 1
  is the YAGNI move; revisit if real-claude smokes show meaningful loss.
