# Milestone 3 (Proposal): Hook-Relayed Tool & Lifecycle Visibility

> Status: **initial proposal**, not yet a committed plan. Reviewed and revised before locking.

## The gap M3 closes

The channel-in/MCP-tools-out shape that M1 delivered and M2 productionizes gives consumers a clean
view of what Claude finally *says* in a turn. `bridge_reply`, `bridge_progress`, and `bridge_done`
carry assistant text at function-call granularity. That's the right contract for "render Claude's
answer in a chat bubble," and it deliberately drops everything that happens between turns.

A rich UI consumer — T3 Code, agtx's per-task render, an orchestrator dashboard — wants more than
the final answer. It wants the timeline: the Bash commands Claude ran mid-turn, the files it
edited, the session lifecycle ("a turn started", "compaction is about to happen"), and the
permission-prompt routing that lets the user say "yes, run that". Channels + the three bridge
tools do not carry any of that. ARCHITECTURE.md's "What channels + MCP doesn't give you" section
names this gap explicitly and points at hooks as the natural extension.

M3 fills roughly the first 60% of that gap by relaying Claude Code hooks (`PreToolUse`,
`PostToolUse`, `Stop`, `SessionStart`, `UserPromptSubmit`, `PreCompact`, ...) into the same
`BridgeEvent` stream that already carries channel messages and MCP tool replies. The remaining
40% — token-level streaming and extended thinking blocks — stays explicitly out of scope. Every
available path to those re-violates a M1.md non-goal.

The `BridgeEvent.tool.event { sessionId, payload: unknown }` variant in
`packages/core/src/events.ts` was reserved during M1 for exactly this. It is currently dead code.
M3 makes it live.

## Goal

M3 wires Claude Code hooks into the bridge so consumers see Claude's tool calls, tool results,
session lifecycle, and prompt-submission events as `BridgeEvent` records in the same JSONL stream
that already carries channel messages and MCP tool replies. After M3, a consumer reading
`events(sessionId)` sees a full timeline of what Claude is doing, not just what it finally said.

## Non-Goals

- Token-level streaming. Every available path (Agent SDK, `--print --output-format stream-json`)
  re-violates M1.md non-goals. The UX delta is "typewriter effect" which most consumers buffer
  anyway. Channels deliberately deliver complete messages, not tokens.
- Extended thinking blocks. Not exposed through any hook that I can identify in the reference.
- Reverse-engineering claude's UI to capture mid-stream text. PTY scraping was ruled out in M1.md.
- Hook-driven behavior modification. PreToolUse hooks *can* block tool calls or rewrite tool
  inputs; M3 is observational only. The relay bin never writes a `permissionDecision` back.
- Hooks for events Anthropic doesn't already provide. M3 is consumption, not protocol extension.

## How hooks work in Claude Code

Hooks are declared in claude's settings.json (user-level `~/.claude/settings.json`, project-level
`.claude/settings.json`, plugin-level `hooks/hooks.json`, or skill/agent frontmatter). Each hook
entry is keyed by an event name; the entry contains a `matcher` (which tools/sources to match)
and a list of `hooks` (the handlers themselves). A handler has a `type` — `command`, `http`,
`mcp_tool`, `prompt`, or `agent` — and runs at the configured lifecycle point.

For a `command` handler, claude spawns the configured shell command, writes the event payload as
JSON to its stdin, and reads JSON from its stdout. The stdout JSON can shape claude's behavior
(block a tool call via `permissionDecision: "deny"`, modify a prompt, etc.). For M3 we mostly want
OBSERVATION, so the relay returns an empty object (or just exits 0) and the side channel of
"bridge gets to see the event" is the entire point.

Hook events relevant to M3, with one-line descriptions:

- `SessionStart` — fires on `startup|resume|clear|compact`; payload includes `session_id`, `cwd`, `model`.
- `SessionEnd` — fires on `clear|resume|logout|bypass_permissions_disabled`; symmetric to `SessionStart`.
- `UserPromptSubmit` — fires when the user (or, for us, the channel) submits a prompt; carries `prompt` text.
- `PreToolUse` — fires before any tool call; carries `tool_name`, `tool_input`, `tool_use_id`.
- `PostToolUse` — fires after a tool call succeeds; carries the same plus the result.
- `PostToolUseFailure` — fires after a tool call fails.
- `Stop` — fires when claude finishes responding (end of turn).
- `PreCompact` / `PostCompact` — fires around context compaction; `matcher` is `manual|auto`.
- `PermissionRequest` — fires when the permission dialog would appear; carries the same tool inputs as `PreToolUse`. This is the candidate hook for permission-prompt routing.
- `Notification` — fires for permission prompts, auth success, elicitation dialogs.

`SubagentStart` / `SubagentStop` exist too, but M3 treats subagents as opaque (their tool calls
will surface via their own `PreToolUse` events with `agent_id` set, which is enough for a timeline
view without special-casing).

## Proposed mechanism: ccb-hook-relay bin

The implementation mirrors the existing `ccb-channel-server` bin pattern. A new bin called
`ccb-hook-relay` is invoked by claude via hook configuration. It:

1. Reads the hook event JSON from stdin.
2. Reads `CCB_BRIDGE_ENDPOINT` and `CCB_SESSION_ID` from the environment (same env vars the
   channel server uses).
3. Opens a short-lived TCP connection to the bridge's `ControlServer` endpoint.
4. Sends a `{type:"hook", event:"<event-name>", payload:<json>}` line over the existing
   JSON-lines control transport, after the existing `hello` handshake.
5. Exits 0 with an empty `{}` on stdout (observation-only; no behavior modification).

A new envelope variant joins the `ControlMessageSchema` discriminated union in
`packages/mcp-channel/src/control.ts`:

```ts
const HookMessageSchema = z.object({
  type: z.literal("hook"),
  event: z.string(),
  payload: z.record(z.string(), z.unknown()),
});
```

`ControlServer` routes incoming `hook` frames to a new `hook` event on its emitter. The
supervisor adapter (M2's `ClaudeCodeSupervisor`, `ServeSupervisor`, and `MockSupervisor`'s test
seam) listens for them and calls the `emit` callback it received from `SupervisorContext` with a
`BridgeEvent` whose shape is the open question below.

User-side configuration: a new `ccb hooks-config` CLI command emits the settings.json snippet to
register the relay for the hook events the user wants surfaced. The snippet looks roughly like:

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "*", "hooks": [{ "type": "command", "command": "ccb-hook-relay", "args": ["PreToolUse"] }] }
    ],
    "PostToolUse": [
      { "matcher": "*", "hooks": [{ "type": "command", "command": "ccb-hook-relay", "args": ["PostToolUse"] }] }
    ]
  }
}
```

The args carry the event name explicitly so the relay does not have to parse stdin twice to
discover what fired. The smoke procedure documents merging this snippet into
`~/.claude/settings.json` or per-project `.claude/settings.json`.

For managed launch (M2's `ClaudeCodeSupervisor.start`), the supervisor can write the hook config
into a temp settings.json and pass `--settings <path>` to `claude`. This stays opt-in via a
`hooks: { events: ["PreToolUse", "PostToolUse", "Stop"] }` option on the supervisor — see the
last open question.

## BridgeEvent shape decisions (open)

The big design question is: do all hook events become `tool.event { sessionId, payload: unknown }`
(preserving the M1 reserved variant), or do they get their own variants (`session.lifecycle`,
`prompt.submitted`, `tool.pre`, `tool.post`, `compact.pending`)?

Trade-offs:

- **One catch-all `tool.event` payload.** Simpler API surface; the union doesn't grow. Consumers
  must introspect the payload to know what they're looking at. Matches the variant M1 already
  reserved. Loses TypeScript discrimination at the consumer boundary, which is the whole point
  of having a discriminated union in the first place.
- **Many specific variants.** Better TypeScript safety. `formatPretty` in `apps/ccb` can render
  each variant with a tailored shape. Widens the public `BridgeEvent` union, which is a stable
  contract — every consumer's exhaustive `switch` has to grow.

Recommended shape: start with the catch-all `tool.event { sessionId, payload }`, where `payload`
is `{ event: string, data: unknown }`. The `event` discriminator is just a string, not a
TypeScript union literal — so adding a new hook event doesn't widen `BridgeEvent`. Consumers that
care can write their own narrower type for the payload. We promote specific variants only when a
concrete consumer reports the introspection-cost is hurting them. This is the YAGNI move and it
keeps the milestone scope small.

The recommendation is reversible: M4 can split `tool.event` into named variants later without
breaking the JSONL store (the payload shape on disk is unchanged; the `BridgeEvent` type widens
in a non-breaking way for the catch-all case and consumers narrow at their convenience).

## Proposed scope

1. **Hook-relay bin** — new `packages/mcp-channel/src/hook-relay.ts` + bin entry. Reads stdin,
   speaks the existing control protocol (with one new envelope variant), exits.
2. **Control protocol extension** — add the `hook` envelope variant to `ControlMessageSchema`,
   route it through `ControlServer`, expose it on the supervisor's `emit` path.
3. **BridgeEvent shape decision** — apply the recommendation above (catch-all `tool.event` with a
   string-discriminated payload). If review pushes back, switch to per-variant before locking.
4. **`ccb hooks-config` CLI subcommand** — emits the settings.json snippet, accepts
   `--events <comma-list>` to scope which hook events to register, accepts `--out <path>` to
   write to a file or `--merge <path>` to splice into an existing settings.json.
5. **Optional managed-launch integration** — `ClaudeCodeSupervisor` accepts a `hooks: {...}`
   option and writes a temp settings.json. Off by default; turning it on is one option flag.
6. **Smoke + docs** — `SMOKE.md` gets a section on hook relay; README gets a one-paragraph
   pointer; a manual smoke against real claude validates `tool.event` records appear in the JSONL.
7. **UI consumer-side rendering** — `formatPretty` in `apps/ccb` handles `tool.event` with a
   reasonable default render (one line per hook event, with the event name and a truncated
   payload preview). If the per-variant path wins later, this becomes per-variant rendering.

## Success Criteria

- A unit test exercises a fake hook payload through the relay bin → `ControlServer` → event
  stream → JSONL store.
- An integration test (gated on `CCB_RUN_REAL_CLAUDE=1`, same gate as M2) confirms real-claude
  hook events show up in the bridge event stream when claude calls Bash / Edit / Write during a
  managed-launch session.
- `ccb hooks-config` emits a valid Claude Code settings.json snippet that a developer can copy
  into `~/.claude/settings.json` or merge in via `--merge`.
- `formatPretty` renders `tool.event` records readably in `ccb demo` output. No raw JSON dumps
  in the default render.
- README cross-links the new behavior; SMOKE.md documents the hook-relay path.
- Token streaming explicitly remains absent (negative criterion: no PR in M3 introduces a
  stream-json reader or a PTY-output parser).
- `bun run lint` and `bun run typecheck` stay green; the existing test suite passes.

## Open Questions

- **BridgeEvent shape (catch-all vs many variants).** Clear lean: catch-all `tool.event` with a
  string-discriminated payload. See the recommendation above. Reversible later. Not lock-blocking.
- **Auto-install vs documented-only hook config.** Auto-modifying a user's
  `~/.claude/settings.json` is intrusive — the user may have unrelated hooks already configured,
  and a botched merge breaks their setup. Documented-only is safer but adds friction. Proposed
  answer: documented-only by default; `ccb hooks-config --merge ~/.claude/settings.json` is an
  explicit opt-in. For managed launch (the M2 path), the temp-settings approach sidesteps the
  question entirely: the spawned `claude` reads a generated settings.json that lives only for
  the session.
- **Project-scoped vs user-scoped hooks.** Does the relay bin only emit for ccb's own sessions,
  or does it intercept all of claude's hook fires? Clear lean: per-session scoping using the
  `session_id` field every hook payload carries. The relay bin compares the incoming
  `session_id` against `CCB_SESSION_ID` and silently exits 0 on mismatch. Cost: a managed-launch
  session id has to match what the hook payload carries — TBD whether claude uses the same id
  for its internal session and for the channel handshake. Genuinely unresolved until verified
  against real claude.
- **Permission-prompt routing.** The channels reference defines a `claude/channel/permission`
  capability for relaying tool-permission prompts. `PermissionRequest` hook fires at roughly the
  same lifecycle point. There's overlap. Genuinely unresolved: does M3 wire BOTH paths, pick
  one, or split permission routing into a smaller follow-up that lands first? Proposed answer:
  defer permission-prompt routing to a sub-task that lands after the rest of M3 is in. M3 ships
  the observational hooks first.
- **Hook scope-creep (observational vs controlling).** PreToolUse can block a tool call by
  returning the right JSON. M3 says strictly observational. But the bin's stdout has to come
  from somewhere, and "empty object" is a deliberate choice. Genuinely unresolved: do we accept
  that bridge consumers will eventually want to route hooks back into control decisions (e.g.
  T3 Code surfacing a permission prompt to the user and writing the user's answer back into the
  hook's stdout)? If yes, the protocol needs a request/response shape, not fire-and-forget. M3
  recommends fire-and-forget; the request/response upgrade is M4 territory.
- **Managed-launch interaction.** When `ClaudeCodeSupervisor.start` generates the per-session
  `.mcp.json`, does it also emit the hook config? Clear lean: yes, via an opt-in `hooks` option
  on the supervisor. Off by default keeps the M2 contract unchanged; on by default would change
  what consumers see in the event stream without them asking for it.
- **Hook envelope size.** PostToolUse for a large Read or a long Bash output can carry kilobytes
  to megabytes of payload. The control protocol's `MAX_FRAME_BYTES = 16 * 1024 * 1024` is a
  generous cap, but writing 16MB JSONL lines is hostile to consumers. Genuinely unresolved:
  should the relay truncate large payloads, or pass them through and let consumers decide?
  Proposed answer: truncate the `tool_input`/`tool_result` fields at a configurable byte budget
  (default ~64KB) and add a `truncated: true` marker. Document the default. Don't truncate
  metadata.

## Out of Scope

- Token streaming.
- Extended thinking surfacing.
- Hook-level claude behavior modification (block tool calls, modify prompts, etc.).
- A separate websocket adapter for hook events. That stays the HTTP/WS adapter's job in a later
  milestone.
- Multi-session hook routing in a daemon. Per M1.md, the bridge is library + per-invocation
  CLI; no daemon.
- Replay-from-cursor for `events(sessionId, {since})` based on hook records. The JSONL store
  records them; cross-process readers and replay are deferred per M2's "Out of Scope".

## What comes after M3

M4 territory: the HTTP/WebSocket adapter (`packages/http`) so non-Node consumers can subscribe to
the now-richer event stream. With hooks landing in M3, the event stream finally carries enough
detail to be worth exposing over a network boundary — before M3, an HTTP consumer would only see
final replies, which is a poor return on the adapter complexity.

M5+ territory: ACP-compatible facade (`packages/acp`); org-level `allowedChannelPlugins` deploy;
permission-prompt routing as a first-class request/response capability (driven by the open
question above); SQLite-backed event store if JSONL hits a query-pattern limit.
