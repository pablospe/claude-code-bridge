# Milestone 2: Real-Claude Productionization

## Goal

M2 makes the bridge runnable against real Claude Code without manual terminal-juggling. The bridge
spawns `claude` itself (managed launch wrapped in node-pty to satisfy the boot-time TTY check),
routes events end-to-end without a human starting `claude` in a second terminal, and degrades
gracefully when the channel server crashes mid-session. The deliverable is `ccb demo
--supervisor=claude "<prompt>"`: one command, one terminal, exits 0 with the event stream printed,
no extra flags, no warnings about an unstarted process, and no human in the loop. The protocol
shape from M1 — inbound on `notifications/claude/channel`, outbound on the three MCP tools,
events persisted as append-only JSONL — does not change. M2 is about closing the gap between
"manual smoke works" and "library is usable by a real consumer."

## Non-Goals

- M2 does not add the HTTP/WebSocket adapter (`packages/http`). Deferred to M3.
- M2 does not add the ACP-compatible facade (`packages/acp`). Deferred to M3.
- M2 does not introduce a long-lived daemon process for shared session state. The bridge is still
  a library plus a per-invocation CLI.
- M2 does not pursue an Anthropic-curated marketplace submission for the bridge plugin. Overlap
  with Remote Control and the curation bar for chat bridges make acceptance unlikely; org-level
  `allowedChannelPlugins` is the realistic publication path.
- M2 does not add cross-process JSONL readers, replay-from-cursor for `events(sessionId,{since})`,
  or a configurable `CCB_WRITE_TIMEOUT_MS` consumer beyond what already exists.

## Scope (in priority order)

### 1. Managed launch (the load-bearing M2 deliverable)

`ClaudeCodeSupervisor` (`packages/claude-code/src/config.ts`) currently throws `"managed launch is
not implemented"` for `start`, `sendMessage`, and `interrupt`. M2 replaces that stub with a real
implementation that owns the `claude` process for the lifetime of a session.

Behavior:

- Wraps `claude` in node-pty because `claude` exits to `--print` when stdout is not a TTY (the
  empirical finding from M1 that motivated `packages/process` in the first place).
- Generates the per-session `.mcp.json` on the fly via an extension of `generateMcpConfig`, writes
  it to a temp path, and passes that path as `--mcp-config`. The temp file is removed on
  `supervisor.close()`.
- Spawns the following command line:

  ```bash
  claude \
    --dangerously-load-development-channels server:ccb \
    --mcp-config <generated> \
    --add-dir <cwd> \
    --strict-mcp-config \
    --allowed-tools "mcp__ccb__bridge_reply mcp__ccb__bridge_progress mcp__ccb__bridge_done"
  ```

  When plugin packaging (scope §2) has landed and the user opts into plugin mode, the
  `--dangerously-load-development-channels server:ccb` flag is replaced with
  `--channels plugin:ccb@ccb-local`. Both modes are supported; the supervisor accepts a
  `channels: "dev-flag" | "plugin"` option (default `"dev-flag"`).
- Auto-confirms the "Loading development channels" warning by buffering PTY output, scanning
  for the warning's confirm hint substring (the "Press Enter to continue" line that the dev
  channels gate prints), and writing `\n` only after the substring appears. The scan is capped
  at 5s; if the substring never appears in that window, the supervisor does NOT send `\n`
  (assume `claude` is already past the prompt or the warning text drifted). This replaces the
  earlier blind 500ms timer, which raced slow boots and misfired on fast ones. Precondition:
  auto-confirm is `dev-flag` mode only; in `plugin` mode the warning does not appear and this
  path is skipped entirely.
- Drops a `start` timeout (default 30s) so a wedged `claude` boot does not hang the bridge
  forever. Timeout fires `supervisor.close` and throws from `start`; `Bridge.startSession`'s
  existing failed-start cleanup tears down the half-built session.
- Tears down the spawned `claude` on `supervisor.close()` with a bounded total budget of 5s.
  The teardown ladder is: write `"/exit\n"` to the PTY and wait up to 1s for graceful exit
  (`/exit` is claude's documented quit slash command; bare `exit` would be sent to the model
  as a user message and produce a stray turn), then SIGINT and wait 1.5s, then SIGTERM and
  wait 1.5s, then SIGKILL. That sums to 4s of bounded waits plus 1s of slack inside the 5s
  total budget.

#### node-pty compatibility constraint

`node-pty` is a native module. Bun's install path may not have a prebuilt binary for the
host platform and may fall back to building from source (which requires a C++ toolchain). If
`node-pty` fails to load at runtime, `ClaudeCodeSupervisor.start` must throw a typed
`LauncherUnavailableError` whose message points the user at the manual-fallback smoke path
in `SMOKE.md`. Bridge core (`packages/core`) must not import `node-pty`; only
`packages/process` does. This keeps the unit-test surface and the consumer-facing library
runnable on hosts where `node-pty` cannot build.

#### Channel-server resolution contract

`generateMcpConfig` is extended to accept an explicit `command` + `args` override. The
managed-launch supervisor passes the absolute path to the Bun binary (`process.execPath` or
the equivalent resolved path) and to `packages/mcp-channel/src/bin.ts`, matching the M1
fix-up in commit `7800f5c` (which moved the manual smoke off the fragile `bunx
ccb-channel-server` PATH lookup). The legacy `bunx ccb-channel-server` default in
`generateMcpConfig` is reserved for users with a globally-installed `claude-code-bridge`
package; managed launch does not rely on it.
- `sendMessage` forwards through the existing `ControlServer.deliver` path. The supervisor does
  not write to the PTY for message delivery — the PTY is the boot substrate only, not a protocol
  path.
- `interrupt` writes a single SIGINT to the spawned `claude` (Ctrl-C from a user's perspective).

Package location: extend `packages/claude-code`; introduce `packages/process` for the node-pty
launcher (deferred from M1 as YAGNI). The launcher is the only file that imports `node-pty`, so
the rest of the workspace stays clean.

Tests:

- Unit tests on the launcher (`packages/process/src/launcher.test.ts`) cover `spawn`, `kill`
  (with each escalation step), `interrupt`, and `close` against a trivial shell command.
- Integration test (`packages/claude-code/src/claude-supervisor.test.ts`) gated on
  `CCB_RUN_REAL_CLAUDE=1`; skipped with a clear `console.log` notice otherwise. The gated test
  drives a full session through the supervisor and asserts `agent.reply{final:true}` lands.

Acceptance: `bun apps/ccb/src/cli.ts demo --supervisor=claude "ping"` succeeds end-to-end against
a real `claude`, prints the event stream, exits 0.

### 2. Plugin packaging (optional alternative channels mode)

Plugin packaging is tracked as task #10 in the parallel queue. Both modes ship in M2; plugin
mode is recommended once `claude plugin install` is documented (see SMOKE.md). The supervisor
accepts a `channels: "dev-flag" | "plugin"` option, default `"dev-flag"` for fresh-clone
friendliness. After task #10 lands, `channels: "plugin"` can use
`--channels plugin:ccb@ccb-local` without `--dangerously-load-development-channels` and
without the boot warning. Users on a stock `claude` (no plugin install) still have a working
path via dev-flag mode.

The plugin manifest already exists at `plugins/ccb/.claude-plugin/`; the M2 work here is limited
to the supervisor flag plumbing and a documented `claude plugin install <path>` step in
SMOKE.md / README.md.

### 3. Supervisor-crash event emission

When the channel server's TCP connection drops mid-session (channel server process killed, OOM,
panic), the bridge currently leaves the session in `state:"open"` indefinitely. The bus and store
keep running, but no further events arrive and consumers have no signal that the agent is dead.

Fix: wire `ControlClient`'s existing `onConnectionLost` callback (`packages/mcp-channel/src/
control.ts:239`) up through the supervisor adapter. On connection loss, the supervisor synthesizes
an `agent.done{reason:"channel-disconnected"}` and a `session.ended{reason:"supervisor crashed"}`
into the bridge via the `emit` callback it received from `SupervisorContext`. The bridge already
treats supervisor-emitted events correctly; the only new piece is the synthesis on the
supervisor side.

`MockSupervisor` gets a corresponding test seam (`triggerCrash()`) so unit tests can exercise
the path without spinning up a real socket pair. `ServeSupervisor` (apps/ccb) gets the same
behavior — currently it owns the `ControlServer`, so the analog is `onSessionLost` when the
peer socket closes.

Tests assert: after a crash event, `bridge.sendMessage` rejects (the session is no longer open),
the JSONL file contains both synthesized events, and `events(sessionId)` terminates cleanly.

### 4. Start timeout for managed launch

The following item was flagged during M1 reviews and is well-motivated by managed launch.

- **`supervisor.start` timeout in `Bridge.startSession`.** A wedged `supervisor.start` currently
  hangs `startSession` forever. Add a configurable `startTimeoutMs` (default 30s) using the same
  `raceWithTimeout` helper already used for `supervisor.close`. On timeout: run the existing
  failed-start cleanup path and throw a typed `StartTimeoutError`.

Deferred from M2:

- Bounded `EventBus` queue with drop policy. M1 reviewers declined this as YAGNI; M2 has not
  changed the event throughput profile, so it stays deferred until a concrete consumer reports
  the failure mode.
- Bounded `Session.pending` Set in `Bridge`. Same reasoning as the bus bound; M2 has not changed
  the event throughput profile, so it stays deferred until a concrete consumer reports the
  failure mode.
- `CCB_DEBUG` env var for verbose bridge logging.
- Configurable `CCB_WRITE_TIMEOUT_MS` for arbitrary consumers (the env var exists but is
  documented as channel-server-internal).
- `tengu_harbor` warning suppression. The Loading development channels warning is one Enter
  press handled by managed launch's auto-confirm; chasing the warning text itself is not worth
  budget.
- `ccb attach <claude-pid>` (attach to an already-running claude). Discovery + state ambiguity
  same as the M1-era discussion; defer past M3 unless a concrete consumer asks.

## Success Criteria

- `bun apps/ccb/src/cli.ts demo --supervisor=claude "hello"` succeeds against a real `claude`
  with no human intervention and exits 0.
- The spawned `claude` is reaped on `bridge.close()`. No orphaned `claude` processes survive a
  clean shutdown; `ps` after `bun apps/ccb/src/cli.ts demo --supervisor=claude` shows nothing.
- All events still persisted to `.ccb-data/<uuid>.jsonl` per M1. The JSONL byte-for-byte format
  does not change.
- When the channel server is killed mid-session (e.g. `kill -9` on the channel-server pid),
  the bridge emits `agent.done{reason:"channel-disconnected"}` and
  `session.ended{reason:"supervisor crashed"}` within ~1s, and `events(sessionId)` terminates.
- `bun run typecheck` and `bun run lint` stay green.
- Each new behavior in §1-§4 has at least one covering unit test; the `CCB_RUN_REAL_CLAUDE=1`
  integration test passes locally; absolute test count is incidental.
- README's first non-mock example is the managed-launch one; SMOKE.md's three-terminal
  procedure is under an `## Advanced fallback` heading.

## Verification status

What's verified on the M2 deliverables as of the milestone close:

- **Protocol shape, library API, MockSupervisor, JSONL store, control protocol, kill ladder,
  crash-event synthesis, start-timeout race fix** — 223 unit/integration tests pass under
  `bun test`; `bun run typecheck` and `bun run lint` clean.
- **Manual three-terminal real-claude smoke** (`docs/SMOKE.md`'s fallback procedure) — works
  end-to-end against `claude` 2.1.143, verified empirically (a turn returns a real reply).
- **Managed-launch boot / teardown lifecycle** — bridge spawns `claude` via PTY, the kill
  ladder reaps it cleanly within the 5s budget. No orphaned `claude` processes observed.

Three real bugs surfaced during end-to-end verification and were fixed:

1. The auto-confirm scanner's hint substring was wrong (`"Press Enter to continue"` vs the
   actual `"Enter to confirm · Esc to cancel"` in claude 2.1.x).
2. The scanner wrote `"\n"` to advance the dev-channels warning; the correct keystroke for
   a TUI reading raw input is `"\r"`.
3. The scanner stayed its hand on timeout, deadlocking the boot on runtimes where PTY
   `onData` callbacks do not fire reliably. Now writes `"\r"` blindly after the scan window.

**Known gap** — the one-command managed-launch demo (`ccb demo --supervisor=claude
"<prompt>"`) is not yet observably producing a reply on a Bun-on-Linux developer host
despite the above fixes. The boot proceeds through the auto-confirm, but the channel server
does not dial back in within `startTimeoutMs`. Diagnosis is blocked by Bun's NAPI compat
layer: PTY `onData` callbacks do not fire under Bun for `node-pty` children, so we cannot
observe what claude prints between `\r` write and channel-server spawn. Two routes to
unblock:

- Build a Node-runnable diagnostic harness that spawns `claude` with the same args as the
  supervisor would, attaches a PTY via `node-pty` under Node (which has working NAPI), and
  tees the PTY output to a file for inspection. This is a standalone diagnostic — it does
  not change production code. Once the post-`\r` claude state is observable, the remaining
  failure mode can be diagnosed and addressed.
- Track the upstream Bun NAPI issue (oven-sh/bun#18546 and adjacent gaps). Once Bun's
  `node-pty` `onData` works natively, the existing scanner code path becomes useful and
  managed launch should work end-to-end under Bun without further changes.

Until one of those lands, the supported real-claude path remains the manual three-terminal
procedure documented in `docs/SMOKE.md`. Programmatic consumers can use `ServeSupervisor`
today; it shares the same protocol with `ClaudeCodeSupervisor` and exercises the
verified-working channel-in / MCP-out chain.

## Open Questions

- Should `--supervisor=claude` be the default and `--supervisor=mock` require opt-in, or the
  other way around? M1's default is `mock`. Argument for flipping: the product is the real
  bridge; `mock` is a test fixture. Argument for keeping `mock` default: a fresh clone with no
  `claude` installed should still get a working `demo`. Current proposed answer: keep `mock`
  default in M2; revisit in M3 once the HTTP adapter has its own surface.
- Should managed launch default to `--channels plugin:ccb@ccb-local` (requires plugin install)
  or `--dangerously-load-development-channels server:ccb` (works everywhere, prints a warning)?
  Proposed answer: default to `dev-flag` because it works without an install step; let users
  opt into `plugin` once they've run `claude plugin install`.
- Permission-prompt handling: `--allowed-tools` is per-session. Should `generateMcpConfig`
  persist it differently (a per-project allowlist), or should the supervisor pass it on every
  spawn? Proposed answer: per-spawn for now; revisit if a consumer reports friction.
- Does `Bridge.startSession`'s new `startTimeoutMs` interact badly with a slow first-time
  `claude` install path (model download, login flow)? Default of 30s is conservative; if
  real-world boots routinely exceed it, the supervisor can pass a higher value.
- Which `node-pty` version should `packages/process` pin? Bun's install path may not have a
  prebuilt binary for every host platform; if it falls back to building from source we need
  to know whether that path works on the project's CI matrix or whether we ship a guard.
- Does `Bridge.startSession` need to detect a `claude` already running in the same workspace
  and refuse to managed-launch a second one? M1.md's `attach` rationale (discovery + state
  ambiguity) applies symmetrically here — two managed launches against the same workspace
  could fight over the same auth/state directory.
- What's the first-run authentication assumption? Managed launch likely fails on a fresh box
  where the user has not run `claude` interactively yet (no cached credentials). Document
  the precondition or detect-and-error with a clear pointer to `claude login`.

## Out of Scope (Deferred to M3+)

- HTTP/WebSocket adapter (`packages/http`).
- ACP-compatible facade (`packages/acp`).
- Cross-process JSONL log handling (multiple readers on the same `.ccb-data/<uuid>.jsonl`).
- Replay-from-cursor for `events(sessionId, {since})` backed by the JSONL store.
- Configurable `CCB_WRITE_TIMEOUT_MS` as a publicly documented knob.
- `CCB_DEBUG` flag for verbose bridge tracing.
- Official Anthropic marketplace submission for the `ccb` plugin (org-level
  `allowedChannelPlugins` is the realistic path).
- `ccb attach <claude-pid>` mode.
- SQLite-backed event store as an alternative to JSONL.
- Daemon mode for shared session state across CLI invocations.
